---

Transitioning `arango-sparql` from a Foxx service to a Python-based microservice (`arango-sparql-py`) while adopting the architectural patterns you established in `arango-cypher-py` is a highly logical and strategic move. Since you are moving to a standalone service, you can leverage rich Python ecosystems for both the Semantic Web (RDF/SPARQL) and AI (for your NL capabilities).

Here is a comprehensive roadmap and advice on how to structure `arango-sparql-py`, based on a review of the repositories you shared.

### 1. Core Transpiler: Parsing and AST (SPARQL to AQL)
In `arango-cypher-py`, you used ANTLR4 to parse Cypher (`arango_cypher/_antlr/Cypher.g4`). 
* **Advice for SPARQL**: While you *could* find a SPARQL 1.1 ANTLR grammar, you have a massive advantage in Python: **`rdflib`**. 
* Python's `rdflib` package has a complete, compliant SPARQL 1.1 parser built-in (`rdflib.plugins.sparql.parser`). 
* Instead of porting `src/lib/sparql-parser.js` and managing your own grammar/AST visitors, you can pass SPARQL strings directly to `rdflib.plugins.sparql.parser.parseQuery()`, which returns a reliable AST (Algebra). 
* You can then write a Python transpiler module (analogous to `translate_v0.py`) that walks this `rdflib` AST and uses an AQL Query Builder (porting your JS `src/lib/aql-query-builder.js` to Python) to generate the final AQL.

### 2. Utilizing `arango-schema-mapper`
In `arango-cypher-py`, you use the OWL schema to bridge the gap between the user's conceptual property graph and the physical ArangoDB schema. For SPARQL, this is an even more natural fit because SPARQL inherently queries RDF/OWL structures!
* **The Strategy**: 
  1. Have `arango-schema-mapper` generate the OWL ontology of the ArangoDB schema.
  2. Load this OWL file into an `rdflib.Graph` in memory when `arango-sparql-py` starts.
  3. During transpilation, when the SPARQL query asks for a specific URI (e.g., `<http://example.org/ontology#Person>`), query your in-memory OWL graph to look up which physical ArangoDB collection and property that URI maps to.
* In your Foxx implementation, you used `src/lib/rpt-translator.js` and `pgt-translator.js` for Relational and Property Graph transformations. The OWL ontology will replace hardcoded mapping configs, making the transpiler dynamic and schema-aware.

### 3. Natural Language to SPARQL (NL2SPARQL)
You built a great foundation in `arango_cypher/nl2cypher/`. You can copy this structure almost exactly for `arango_sparql/nl2sparql/`.
* **Prompt Engineering**: Provide the LLM with the OWL ontology (or a simplified TTL/Turtle version of it, as LLMs read Turtle very well) generated by `arango-schema-mapper`. 
* Instruct the LLM: *"Generate a SPARQL 1.1 query based on the following RDF/OWL schema. Return only the SPARQL..."*
* **Evaluation (`tests/nl2cypher/eval`)**: Keep your few-shot prompting and evaluation pipelines. You can easily adapt your baseline testing frameworks to compare expected SPARQL vs. generated SPARQL.

### 4. Rigorous Testing & Reference Databases
For Cypher, you are using the openCypher TCK (Test Compatibility Kit) and Neo4j CE as your ground truth.
* **The SPARQL TCK Equivalent**: Use the **W3C SPARQL 1.1 Evaluation Test Suite** (DAWG tests). It is the gold standard for SPARQL processors. It contains hundreds of queries, input RDF data, and the expected output bindings. You can build a harness analogous to `tests/tck/runner.py`.
* **The Reference Database**: Instead of Neo4j, you need a robust, open-source RDF triplestore to run the W3C tests against and compare results with ArangoDB. I highly recommend **Apache Jena Fuseki** or **Oxigraph**.
  * **Oxigraph**: An embedded graph database written in Rust with excellent Python bindings (`pip install oxigraph`). It is strictly W3C compliant, blazing fast, and doesn't require a separate Docker container to run your test suite against. It is perfect for integration testing.
  * **Apache Jena Fuseki**: If you prefer a server-based approach via `docker-compose.yml` (like you did with Neo4j), Jena Fuseki is the enterprise open-source standard for SPARQL.

### 5. UI and Frontend (`ui/`)
Your React/Vite/TypeScript setup in `ui/` is highly reusable. 
* **Editor**: Swap the Cypher syntax highlighter in `CypherEditor.tsx` with a SPARQL one. If you are using CodeMirror, you can use `@codemirror/legacy-modes/mode/sparql`.
* **Graph Visualization**: Your `CytoscapeGraph.tsx` will need a slight adjustment. In Cypher, nodes have many properties. In strict RDF/SPARQL, everything is a triple (Subject-Predicate-Object), meaning properties are technically also graph nodes. You will likely want to implement a UI toggle that "collapses" literal nodes into properties on the Subject node to make the Cytoscape graph readable for the user.

### Suggested Execution Plan

1. **Scaffold**: Clone `arango-cypher-py`. Rename modules to `arango_sparql`. Rip out the `arango_cypher/_antlr` directory and replace it with `rdflib`.
2. **Translate API**: Port `src/lib/aql-query-builder.js` from the old repo into Python. Build the new AST walker that takes `rdflib.plugins.sparql.parser` output and feeds it to the query builder.
3. **Integrate Mapper**: Hook up `arango-schema-mapper` to feed the OWL representation into the translator context so URIs are resolved dynamically.
4. **Test Suite**: Add Oxigraph to your `tests/` folder. Download the W3C SPARQL test suite. Write a `tests/w3c/runner.py` (similar to your TCK runner) that tests Oxigraph output vs. ArangoDB output.
5. **NL2SPARQL**: Adapt the LLM prompts to output SPARQL using Turtle definitions.
6. **UI**: Adapt the React frontend for SPARQL syntax and RDF-style graph rendering.
