## Root cause (diagnosed, not fixed — out of this plan's file scope)
`tests/nl2sparql/eval/runner.py::_judge_execution` (Plan 01) contains, by design:
```python
gold_sparql = expected.replace("xsd:int(", "xsd:integer(")   # gold only
...
cand_result = oxi_query(store, outcome.sparql)                # candidate: NEVER rewritten
```
This was an intentional Plan 01 design choice ("Anti-Pattern from RESEARCH: never rewrite the candidate's own SPARQL text, so a candidate's genuine engine rejection stays a judged, tagged outcome"), and 07.2-RESEARCH.md explicitly predicted gold-vs-gold would be 1.0 as a "self-consistency check on the new judge." That prediction is falsified for the scripted provider specifically: `tests/nl2sparql/eval/runner.py::_client_for` builds the scripted candidate as `case.get("scripted", case["expected"])` — i.e. for every CK25 case without a `scripted:` override (all 49), the candidate SPARQL text handed to the judge is **byte-identical** to the gold text. For `ck25-37` and `ck25-42` (the two corpus cases confirmed by 07.2-RESEARCH.md to contain `xsd:int(`), that shared text contains `xsd:int(`:
- Gold side: normalized to `xsd:integer(` → pyoxigraph accepts it, executes, returns rows.
- Candidate side: same original text, `xsd:int(` left untouched → pyoxigraph raises `RuntimeError: The custom function <...#int> is not supported` → `candidate_engine_rejected`.

Because gold and candidate are asymmetrically normalized, a gold graded against its own verbatim text now diverges whenever that text contains `xsd:int(`. This is a defect in Plan 01's judge (the gold-side-only normalization is unsafe as a general design whenever gold and candidate coincide), not a defect in this plan's config flip, corpus, or vendored data.
