<objective>
Build the answer-set execution judge (NL-EVAL-05, D-02..D-05): run gold + candidate
SPARQL through pyoxigraph and compare ANSWERS instead of query structure. Relax the
existing `_judge_execution` stub from `(var,value)`-pair comparison to a var-rename-
insensitive, duplicate-safe value-set comparison with IRI↔label normalization, an ASK
branch, a verified-safe gold `xsd:int(` → `xsd:integer(` normalization, and distinctly-
tagged D-05 exception buckets (gold-engine-limit vs candidate-engine-reject). Isolate the
pyoxigraph API behind a new `oxi_query()` helper in `tests/helpers/oxi.py` (rule 200), and
add the single corpus-level `data_path` read in `run()` that threads the shared instance
graph into the judge.

CRITICAL wiring: the `_judge` dispatcher must actually FIRE the execution path when a config
sets `judge: execution`. CK25 cases carry NO per-case `data:` field — the instance graph is a
CORPUS-LEVEL `data_path:` key (D-02 / Pitfall 1). So `_judge` must grow to a 4-arg
`_judge(judge_name, case, outcome, data_ttl=None)` signature (RESEARCH architecture, ~line 99)
whose guard fires on the corpus-level `data_ttl`, not solely on `case.get("data")`. Without this
change, flipping configs to `judge: execution` (Plan 03) changes nothing and the sweep silently
reproduces the canonical 0% floor this phase exists to eliminate.

Purpose: The canonical exact-algebra judge floors real LLM output at 0% on CK25 (07.1
finding); this judge makes adopted-benchmark eval meaningful by grading on answers.
Output: A working, unit-tested, no-network execution judge — the core of this phase.
</objective>
