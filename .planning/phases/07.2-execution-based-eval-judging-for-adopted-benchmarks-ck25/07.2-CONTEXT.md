# Phase 07.2: Execution-based eval judging for adopted benchmarks (CK25) - Context

**Gathered:** 2026-07-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Make adopted-benchmark NL→SPARQL eval **meaningful** by grading on ANSWERS instead of
query structure. 07.1's live run proved the canonical exact-algebra judge floors real
LLM output at 0% on QALD/CK25 (golds pre-resolve entity IRIs + fix projections the model
can't reproduce from NL + schema). This phase adds an opt-in **answer-set execution
judge** (pyoxigraph), vendors the **CK25 instance graph**, and records CK25's first real
end-to-end NL→SPARQL accuracy number as the corporate-domain anchor.

Delivers: a working execution judge + vendored CK25 instance data + a recorded live
CK25 accuracy number. Does NOT deliver QALD execution grading (own later phase), an
ArangoDB execution path, or a model-quality improvement (measurement only, not tuning).
</domain>

<decisions>
## Implementation Decisions

### Scope
- **D-01 (LOCKED):** **CK25 now; QALD later.** Land execution grading fully for CK25
  (instance data is small, self-contained, already fetched during the spike). QALD's
  heavier DBpedia answer-subset capture is deferred to its own later phase. Rationale:
  fastest path to one real, maintained number; QALD subsetting is a separate risk.

### Execution engine
- **D-02 (LOCKED):** **pyoxigraph only.** Grade by running gold + candidate SPARQL through
  pyoxigraph (the repo's W3C ground-truth engine) — deterministic, no DB, no network.
  NO transpiler→AQL→ArangoDB execution path this phase. Rationale: this judges the
  *model's SPARQL correctness* (the NL→SPARQL quality metric); the transpiler's AQL
  correctness is already covered by the W3C DAWG suite. Keeps the judge CI-friendly.

### Correctness definition
- **D-03 (LOCKED):** **Answer-set equality up to variable renaming + IRI↔label
  normalization.** Compare the set of answers (not `(var,value)` pairs — gold projects
  `?result`, model projects `?department`/`?phone`), and treat an entity's IRI and its
  label as equivalent (so returning a manager's name vs IRI both count). The spike showed
  ≥2 cases (ck25-31, ck25-32) that need exactly this normalization. NOT partial-credit/F1
  — binary answer-set match this phase (F1 deferred).

### Judge must handle (from spike evidence — see 07.2-SPIKE-FINDINGS.md)
- **D-04:** **SELECT and ASK.** pyoxigraph returns a `QueryBoolean` for ASK (spike cases
  ck25-16/28/33 errored on `.variables`); the judge needs an ASK branch comparing the boolean.
- **D-05:** **Classify gold-side engine limits vs model errors.** Some gold queries use
  functions pyoxigraph rejects (`xsd:int()` — ck25-37/42); some model queries the
  transpiler accepts but oxigraph's parser rejects (`%`-encoded IRI / prefix — ck25-5/18/26).
  These must be surfaced/labelled, not silently scored as model failures. Planner decides
  exact handling (documented skip vs normalization) — flag counts must be visible, never
  silently truncated.

### Opt-in & non-regression
- **D-06 (LOCKED):** Execution judging is **opt-in per config** via `judge: execution`
  (mirrors the existing `judge: canonical`). The `scripted` canonical config stays the
  no-network CI default; W3C DAWG ≥ 96.4% guard and the deterministic transpiler are
  untouched; no secrets or raw prompts committed (reports stay gitignored).

### Baseline recording
- **D-07 (LOCKED):** Record a `scripted-ck25` execution-graded entry (gold-vs-gold sanity
  = 100%) AND a live `openai-gpt4o-mini-ck25` execution-graded accuracy number in
  `baseline.json` — **reported, NOT gated** (CK25 is the directional anchor per 07.1 D-03;
  N=49 → MDE ~18–20pt, too small to gate). Per-set entries stay separate/un-blended
  (07.1 Pitfall 3).

### Claude's Discretion
- Exact judge module layout, normalization implementation, and how ASK/unsupported-gold
  cases are represented in results — planner/executor decide, consistent with the reusable
  assets below.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `_judge_execution(expected, outcome, data_ttl)` in `runner.py` already loads a Turtle
  fixture via `tests.helpers.oxi.load_store_from_string`, runs both queries, and compares
  `sorted(map(_canon_row, ...))`. 07.2 relaxes it: value-set (not var-keyed) comparison,
  IRI↔label normalization, ASK handling, and a per-case `data:` fixture wired for CK25.
- `_judge` dispatch already routes `judge == "execution" and case.get("data")` → so the
  wiring hook exists; CK25 cases need a `data:` reference (shared instance graph) + configs
  set `judge: execution`.
- `oxi.py` helpers give binding extraction + row canonicalization to build on.

### Established Patterns
- Per-set separate baseline entries with provenance fields (07.1) — extend, don't blend.
- Vendored data carries a NOTICE.md + passes `test_vendored_provenance.py` (07.1 guard).
- Live path reads `NL2SPARQL_API_KEY`, `RUN_EVAL=1`; reports/ gitignored; fold-in manual.

### Integration Points
- `configs.yml` `openai-gpt4o-mini-ck25` / `scripted-ck25` gain `judge: execution` + a
  `data:` fixture pointer; `baseline.json` gains execution-graded per-set entries.
- Instance graph vendored under `tests/nl2sparql/eval/vendored/ck25/` (new file + NOTICE update).
</code_context>

<specifics>
## Specific Ideas

- The spike's throwaway judge used "multiset of frozenset-of-values-per-row" for var-rename
  insensitivity — a reasonable starting point for the SELECT path; harden it (IRI/label
  norm, ASK) for the real judge.
- Expected clean CK25 live number after ASK + IRI/label handling: ~10–16% (spike floor was
  8.2% strict). A low-but-real anchor is the point (headroom for future few-shot/grounding).
</specifics>
