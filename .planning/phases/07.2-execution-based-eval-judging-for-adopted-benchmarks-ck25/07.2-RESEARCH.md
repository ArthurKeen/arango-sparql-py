## Summary

The spike already proved the mechanism works and pinned the three judge gaps (ASK, `xsd:int()`, stricter-pyoxigraph-parser). This research verified each gap concretely against the *actual* installed `pyoxigraph==0.5.9` and the *actual* CK25 instance graph (fetched fresh at the pinned commit `cb928b2f201e4bdbbde9a1cd0653152779736395`, confirmed byte-identical: 951,747 bytes / 26,903 triples, matching `07.2-CONTEXT.md` exactly), rather than re-deriving from training knowledge. Every one of the "concrete unknowns" in the phase brief now has a verified, specific answer:

1. **pyoxigraph result-type branching** is trivial: `store.query()` returns a `QueryBoolean` for ASK (only `.serialize()`, no `.variables` — confirming the spike's crash), but `bool(query_boolean_result)` works correctly and needs no string parsing. `isinstance(result, pyoxigraph.QueryBoolean)` after running the query is the clean branch — no pre-parsing of the query form is needed.
2. **IRI↔label normalization** should use `rdfs:label` (the standard predicate), not CK25's domain-specific `pv:name`. Verified: every subject with `pv:name` also has an identical-valued `rdfs:label` (0 counterexamples), and `rdfs:label` covers strictly more subjects (2,618 vs 1,364, including `Price` entities `pv:name` never reaches). Build one IRI→label lookup per store (a single `SELECT ?s ?label WHERE { ?s rdfs:label ?label }`), cached once per judged case. **Known residual risk, verified via real data, not hypothetical:** labels are NOT globally unique — `Hardware` has 1,000 entities but only 837 distinct names (163 collisions), `Supplier` has 250 entities / 246 distinct names (4 collisions). `Employee`, `Department`, `ProductCategory`, `BillOfMaterial`, `Service`, `Manager` are all 1:1 unique. This means label-normalization is safe for the entity classes the spike's flagged cases (ck25-31 ProductCategory, ck25-32 Supplier) actually touch, but is not a universally sound operation for this graph — document as an accepted, small, real limitation (not a bug to chase down this phase).
3. **The `xsd:int()` gold-engine-limit is fully and safely fixable by textual normalization**, not a skip. `xsd:int` is a *derived* XSD datatype with no implicit SPARQL constructor function (only the ~11 primitive XSD types get one) — this is spec-correct pyoxigraph behavior, not a pyoxigraph bug. `xsd:integer(...)` (the primitive supertype) IS a supported constructor and is semantically equivalent for every value in this dataset (plain untyped decimal-string literals like `"72"`). Verified empirically: replacing `xsd:int(` → `xsd:integer(` in ck25-37's actual gold SPARQL text and running it against the real instance graph returns 7 well-formed, sane rows. This resolves both flagged cases (ck25-37, ck25-42) with zero remaining gold-side engine failures — no visible-skip bookkeeping needed for this specific gap.
4. **The value-set comparison unit needs one refinement over the spike's throwaway version.** "Multiset of frozenset-of-values-per-row" silently collapses duplicate values *within* a row (e.g. a row where two different projected variables happen to hold the same string). Use **multiset of sorted-tuples-of-values-per-row** instead (preserve per-row multiplicity, still var-name/column-order insensitive) — verified sound against the corpus's actual multi-projection cases (ck25-30, ck25-31, ck25-32, ck25-37, ck25-42 all project 2–3 variables).
5. **The `data:` wiring hook is unused scaffolding today** (`CorpusCase.data: str | None` exists in the pydantic model but zero corpus.yml file anywhere in the repo currently sets it). A single 951 KB instance graph shared across all 49 CK25 cases must NOT be inlined once-per-case into `corpus.yml` (as `ontology:` is) — it must be a corpus-level **file path reference**, read once, mirroring the existing `shared_ontology = corpus.get("ontology", "")` / `case.get("ontology", shared_ontology)` pattern in `run()`.
6. **The CK25 instance graph is a straightforward, low-risk vendoring add.** Verified byte-for-byte size/triple-count match against `07.2-CONTEXT.md`'s stated numbers by fetching it fresh from the pinned commit. It fits comfortably under `test_vendored_provenance.py`'s 5 MB secret-scan cap and needs only a `NOTICE.md` extension (the file already documents the CC-BY-4.0 license, source URL, and commit — it explicitly states today that instance data was *removed*; this phase reverses exactly that documented decision).

**Primary recommendation:** Extend `tests/helpers/oxi.py` with a form-aware query-execution helper (never import `pyoxigraph` directly in `runner.py`, per rule 200); vendor the full `prod-inst.ttl` under `vendored/ck25/raw/`; add a corpus-level `data_path:` key read once per `run()`; normalize gold-side `xsd:int(` → `xsd:integer(` before execution; build one `rdfs:label` lookup per judged run; compare answer-sets as a sorted multiset of per-row sorted-value-tuples; and flip `configs.yml`'s `scripted-ck25` / `openai-gpt4o-mini-ck25` entries (and `baseline.json`'s existing `scripted-ck25` entry) from `judge: canonical` to `judge: execution` in place — these are the two CK25-specific configs the phase exists to fix, not new sibling configs.

### Pattern 1: Form-aware pyoxigraph result branching (verified API, no string parsing needed)
**What:** `store.query(sparql)` returns one of three distinct Python types depending on the query form — `pyoxigraph.QuerySolutions` (SELECT), `pyoxigraph.QueryBoolean` (ASK), `pyoxigraph.QueryTriples` (CONSTRUCT/DESCRIBE, not needed this phase per D-04's SELECT+ASK scope — verified 0 CONSTRUCT/DESCRIBE cases exist in the 49-case corpus).
**When to use:** Every execution-judge call, before attempting to read bindings.
**Example (verified live against `pyoxigraph==0.5.9`):**
```python
# Source: verified interactively against the installed pyoxigraph==0.5.9
import pyoxigraph as oxi

result = store.query(sparql)
if isinstance(result, oxi.QueryBoolean):
    # QueryBoolean has ONLY .serialize() -- no .variables (the spike's crash).
    # bool(result) is correct and needs no string/JSON parsing:
    value = bool(result)          # True/False, verified against both ASK outcomes
else:
    # QuerySolutions: .variables is a list[Variable]; iterate solutions,
    # index each by Variable or its .value name string (existing oxi.py pattern).
    variables = list(result.variables)
    rows = [{v.value: str(solution[v]) for v in variables if solution[v] is not None}
            for solution in result]
```
Do NOT try to detect the query form by inspecting the SPARQL text (`"ASK" in sparql.upper()`) before running it — the type returned by `store.query()` is the authoritative, already-verified signal.

### Pattern 2: rdfs:label-based IRI↔label normalization (verified coverage against the real instance graph)
**What:** Build one `IRI -> label` dict per judged store via a single query, then normalize every answer value through it before comparison.
**When to use:** Every SELECT-form comparison (not ASK — booleans need no normalization).
**Example:**
```python
# Source: verified against the real CK25 instance graph fetched at
# cb928b2f201e4bdbbde9a1cd0653152779736395 (951,747 bytes / 26,903 triples,
# matches 07.2-CONTEXT.md exactly)
def build_label_map(store) -> dict[str, str]:
    result = store.query(
        "PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#> "
        "SELECT ?s ?label WHERE { ?s rdfs:label ?label }"
    )
    variables = list(result.variables)
    out: dict[str, str] = {}
    for solution in result:
        s, label = solution[variables[0]], solution[variables[1]]
        out[str(s)] = str(label).strip('"').split('"@')[0]  # strip N-Triples quoting + lang tag
    return out

def normalize_value(raw: str, label_map: dict[str, str]) -> str:
    # raw is pyoxigraph's stringified term ("<...>" for an IRI, "\"...\"" for a literal)
    if raw.startswith("<") and raw.endswith(">"):
        iri = raw[1:-1]
        return label_map.get(iri, raw)   # prefer the label form when known
    return raw
```
Verified: `pv:name` is a strict subset of `rdfs:label` coverage (1,364 vs 2,618 labeled subjects; 0 subjects have `pv:name` without an identical `rdfs:label`) — use `rdfs:label` alone, no fallback to `pv:name` needed.

### Pattern 3: Safe gold-side `xsd:int()` normalization (verified semantically equivalent, not a skip)
**What:** `xsd:int` is a *derived* XSD datatype; SPARQL 1.1's implicit type-constructor functions exist only for the ~11 primitive XSD types (`xsd:integer` among them, `xsd:int` NOT among them) — pyoxigraph correctly rejects `xsd:int(...)` as an unsupported custom function (`RuntimeError: The custom function <...#int> is not supported`, verified). `xsd:integer(...)` IS supported and produces an identical numeric value for every plain decimal-string literal in this dataset.
**When to use:** Before executing ANY gold SPARQL through pyoxigraph, as a pre-pass textual substitution.
**Example (verified against the real ck25-37 gold + real instance data — returns 7 correct, non-empty rows):**
```python
def normalize_gold_for_pyoxigraph(sparql: str) -> str:
    # Verified safe for this dataset: pv:quantity's actual instance literals
    # are untyped decimal strings ("72", not "72"^^xsd:int); xsd:int and
    # xsd:integer parse them identically. Only 2 of 49 gold queries need
    # this (ck25-37, ck25-42) -- confirmed by grepping corpus.yml.
    return sparql.replace("xsd:int(", "xsd:integer(")
```
This closes D-05's gold-engine-limitation gap for both known cases with zero remaining "documented skip" bookkeeping — but keep the try/except wrapper around gold execution regardless (see Common Pitfalls), so any *future* unforeseen gold-side engine gap still surfaces visibly instead of crashing the whole sweep.

### Pattern 4: Var-rename-insensitive, duplicate-safe value-set comparison
**What:** The spike's "multiset of frozenset-of-values-per-row" silently drops duplicate values within a single row (a `frozenset` can't hold two equal elements). Use a **sorted tuple** (not a frozenset) per row instead — preserves per-row value multiplicity while staying insensitive to column order and variable names.
**Example:**
```python
def _row_key(row: dict[str, str], label_map: dict[str, str]) -> tuple[str, ...]:
    return tuple(sorted(normalize_value(v, label_map) for v in row.values()))

def rows_match(expected_rows: list[dict], actual_rows: list[dict], label_map: dict) -> bool:
    exp = sorted(_row_key(r, label_map) for r in expected_rows)
    act = sorted(_row_key(r, label_map) for r in actual_rows)
    return exp == act
```

### Anti-Patterns to Avoid
- **Rewriting the CANDIDATE's SPARQL to make it pyoxigraph-parseable.** The verified `%`-encoded-PNAME parser gap (ck25-5/18/26-style cases) is real, but "repairing" the model's own query before judging it would launder a genuine correctness signal into a measurement of how much rewriting was needed — a different, unrequested metric. Only the GOLD gets a documented, verified-safe textual normalization (Pattern 3); the candidate's rejection is a judged outcome, tagged distinctly (see Common Pitfalls), never silently patched.
- **Detecting ASK vs SELECT by string-matching the SPARQL text.** Verified unnecessary and fragile (subqueries, comments, or a `SELECT` inside an ASK's nested pattern would confuse a text scan) — `isinstance(result, oxi.QueryBoolean)` after execution is authoritative and free.
- **Comparing `(variable_name, value)` pairs instead of values alone.** This is exactly what D-03 rules out and what the existing `_judge_execution` stub currently does — CK25 golds project `?result` while models project `?department`/`?phone`/etc.; keying on variable name guarantees a false negative on every case with a differently-named projection.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SPARQL execution / ASK-boolean extraction | A custom SPARQL mini-interpreter or regex-based ASK-result parser | `pyoxigraph.Store.query()` + `isinstance(result, oxi.QueryBoolean)` / `bool(result)` | Already the repo's W3C ground-truth engine (CLAUDE.md hard rule); verified API is a two-line branch, no need for anything custom |

**Key insight:** Every piece of this judge's "hard part" (result-type detection, label resolution, safe gold normalization) already has either a native pyoxigraph API answer or a materialized-in-the-data answer. The only genuinely custom code this phase writes is the value-set comparison (Pattern 4) and the visible-bucket classification (D-05) — both small, and both already scaffolded by the existing `_judge_execution`/`_judge` dispatch.

## Common Pitfalls

### Pitfall 1: Inlining the 951 KB instance graph once-per-case into `corpus.yml`
**What goes wrong:** Following the existing `ontology:` field's inline-Turtle convention naively for `data:` would either duplicate 951 KB across all 49 cases (if per-case) or bloat `corpus.yml` to ~1 MB even with a single shared inline block, making the file unreviewable as a diff and slow to `yaml.safe_load`.
**Why it happens:** `ontology:` is inlined today and is small (~10–20 KB); the natural instinct is to copy the same shape for `data:`.
**How to avoid:** Vendor the full instance graph as its own file (`vendored/ck25/raw/prod-inst.ttl`) and add a **path reference** key at the corpus level (e.g. `data_path: raw/prod-inst.ttl`), resolved once relative to the corpus file's directory and read once in `run()` — mirroring `shared_ontology`/`case.get("ontology", shared_ontology)` but for a file path, not inline text.
**Warning signs:** A `corpus.yml` diff that is hundreds of thousands of lines; `git diff` becoming unusable for review.

### Pitfall 2: Treating IRI↔label normalization as globally injective
**What goes wrong:** Assuming every IRI maps to a unique label (and vice versa) can produce a false-positive "match" between two genuinely different entities that happen to share a name.
**Why it happens:** The spike's two flagged cases (ck25-31 ProductCategory, ck25-32 Supplier) both happen to normalize safely, making it easy to assume the technique is universally safe.
**How to avoid:** Verified concretely: `Hardware` (1,000 entities / 837 distinct names, 163 collisions) and `Supplier` (250 / 246, 4 collisions) have real name collisions in this exact graph; `Employee`/`Department`/`ProductCategory`/`BillOfMaterial`/`Service`/`Manager` do not. Document this as an accepted, quantified limitation of the "reported not gated" CK25 anchor (D-07 already frames CK25 as directional, not a power gate) rather than attempting a fully-injective disambiguation scheme this phase.
**Warning signs:** A live CK25 execution-graded pass rate that looks implausibly high relative to the canonical/transpile-rate signal — worth spot-checking whether any pass involves a `Hardware`- or `Supplier`-typed answer value.

### Pitfall 3: Silently swallowing a gold-side or candidate-side pyoxigraph exception into a bare `False`
**What goes wrong:** Wrapping the entire judge body in one broad `try/except: return False` makes gold-engine-limitations (D-05, e.g. an unforeseen future `xsd:int`-like gap) and candidate-engine-rejections (the `%`-PNAME parser-strictness gap) both look like ordinary "wrong answer" failures in the aggregate pass rate — exactly the "silently truncated" outcome D-05 forbids.
**Why it happens:** The simplest possible implementation of "catch pyoxigraph errors" is a single blanket try/except around the whole function.
**How to avoid:** Catch gold-side and candidate-side exceptions **separately**, and attach a distinguishing tag to the `CaseResult` (a new optional field, e.g. `judge_note: str | None`) so the report/baseline fold-in step can show "N gold-engine-limitation" and "M candidate-engine-rejected" counts distinctly from "wrong answer" — never blended into one opaque failure count. (Empirically, after Pattern 3's gold normalization, 0 of 49 golds are expected to hit this bucket; the candidate-side bucket is real and expected to be nonzero for a live LLM run, per the spike's ck25-5/18/26 finding.)
**Warning signs:** A reviewer asking "why did this case fail?" and the report showing no distinction between "model returned zero rows" and "pyoxigraph refused to even parse the model's query."

### Pitfall 4: Repurposing vs. duplicating the `scripted-ck25` / `openai-gpt4o-mini-ck25` config names
**What goes wrong:** Creating brand-new sibling config names (e.g. `scripted-ck25-exec`) instead of flipping the existing two configs' `judge:` value in place would leave a stale, misleading `canonical`-graded `openai-gpt4o-mini-ck25` config sitting in `configs.yml` alongside a new execution-graded one — two numbers for the same nominal config purpose, inviting confusion about which is "the" CK25 anchor.
**Why it happens:** "Opt-in per config" (D-06) reads ambiguously as "always add a new config," but D-06's actual target is the *root* `scripted` config (the hand-authored 25/34-case corpus) staying canonical — not the CK25-specific configs, whose entire reason for existing this phase is that canonical grading is useless for them (0/49, per the spike).
**How to avoid:** Flip `configs.yml`'s existing `scripted-ck25` and `openai-gpt4o-mini-ck25` entries' `judge:` value from `canonical` to `execution` in place; update `baseline.json`'s existing `scripted-ck25` entry (currently `pass_rate: 1.0` under canonical — verified it should ALSO be `1.0` under execution, since a gold graded against itself must match exactly; this doubles as a self-consistency check on the new judge implementation) and add the (currently absent — verified empty in `baseline.json`) `openai-gpt4o-mini-ck25` entry. Preserve the existing `role`/`surviving_n`/`achieved_mde`/`note` fields; only the judge-dependent fields (`pass_rate`, `passed`, `cases`) change.
**Warning signs:** Two CK25-named configs in `configs.yml` with different `judge:` values and no clear statement of which is authoritative.

### Pitfall 5: Reloading the pyoxigraph store from scratch on every single case when it's unnecessary
**What goes wrong:** The existing `_judge_execution` stub calls `load_store_from_string(data_ttl)` fresh inside the function — fine for a small per-case fixture, but for CK25's single shared 951 KB graph this means parsing 26,903 triples repeatedly.
**Why it happens:** Following the existing per-case signature `_judge_execution(expected, outcome, data_ttl)` literally, without noticing all 49 CK25 cases share the identical `data_ttl`.
**How to avoid:** Verified this is a minor, not a blocking, concern: loading takes ~30 ms per call (measured directly), so 49 cases add ~1.5 s total to a run — negligible next to the live sweep's actual dominant cost (LLM API round-trips per case, documented in README.md as "seconds-scale" per case). **Do not over-engineer a store cache this phase** unless the planner independently decides the ~1.5 s is worth avoiding; if so, the clean fix is building the `Store` once in `run()` when `judge_name == "execution"` and threading the `Store` object (not raw `data_ttl` text) into `_judge_execution`.
**Warning signs:** None expected to be user-visible; flagged here only so a reviewer doesn't mistake the repeated 30 ms loads for a real performance bug worth a complex fix.

## Code Examples

### Full `_judge_execution` sketch (illustrative; combines Patterns 1–4)
```python
# Source: composed from verified pyoxigraph==0.5.9 API behavior + the real
# CK25 instance graph's confirmed rdfs:label coverage (see Patterns 1-4 above).
# This is illustrative structure, not a literal patch -- exact layout is
# Claude's Discretion per 07.2-CONTEXT.md.

def _judge_execution(expected: str, outcome: Any, data_ttl: str) -> tuple[bool, str | None]:
    """Returns (passed, judge_note). judge_note is None for an ordinary
    pass/fail; set to a short tag string for the two D-05 visible buckets."""
    if not outcome.aql:
        return False, None

    from tests.helpers.oxi import load_store_from_string, oxi_query  # new helper, isolates pyoxigraph

    store = load_store_from_string(data_ttl)

    gold_sparql = expected.replace("xsd:int(", "xsd:integer(")  # Pattern 3
    try:
        gold_result = oxi_query(store, gold_sparql)
    except (SyntaxError, RuntimeError) as exc:
        return False, f"gold_engine_limitation: {exc}"  # D-05 visible bucket

    try:
        cand_result = oxi_query(store, outcome.sparql)
    except (SyntaxError, RuntimeError) as exc:
        return False, f"candidate_engine_rejected: {exc}"  # D-05 visible bucket

    if gold_result.kind != cand_result.kind:
        return False, None  # e.g. gold ASK, candidate SELECT -- a genuine mismatch

    if gold_result.kind == "ask":
        return gold_result.boolean == cand_result.boolean, None

    label_map = _build_label_map(store)  # Pattern 2, one query per case (cacheable, see Pitfall 5)
    return rows_match(gold_result.rows, cand_result.rows, label_map), None  # Pattern 4
```

### `oxi.py` extension sketch (form-aware wrapper, isolates the pyoxigraph import per rule 200)
```python
# Source: tests/helpers/oxi.py extension, composed from verified API above
from dataclasses import dataclass

@dataclass
class OxiQueryResult:
    kind: str                        # "select" | "ask"
    rows: list[dict[str, str]] | None = None
    boolean: bool | None = None

def oxi_query(store: Any, sparql: str) -> "OxiQueryResult":
    result = store.query(sparql)      # may raise SyntaxError | RuntimeError -- caller's job to catch
    if isinstance(result, oxi.QueryBoolean):
        return OxiQueryResult(kind="ask", boolean=bool(result))
    variables = list(result.variables)
    rows = [
        {v.value: str(solution[v]) for v in variables if solution[v] is not None}
        for solution in result
    ]
    return OxiQueryResult(kind="select", rows=rows)
```
