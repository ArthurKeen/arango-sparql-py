<objective>
Re-point `NlPipeline.run()` off its private `PromptBuilder` → `LLMClient` →
`RepairLoop` loop and onto `arango_query_core.nl.NLQueryEngine`, wired with the
`EngineProviderBridge` + `SparqlAdapter` from plan 06.1-02. The `SparqlAdapter` is
constructed with `resolver=self.resolver` (the pipeline's own resolver, which may
come from a mapping-JSON or analyzer-enriched request) and `ontology_ttl=self.ontology_ttl`
(prompt text only), so `validate()` and the final re-translate always share one schema.
Map the engine's `NLResult` back to the public `PipelineOutcome` shape — re-translating
the final query ONCE (deterministic, cheap) to recover the `aql`/`bind_vars` the
`validate()` seam discards. Because that final re-translate passes `params` (unlike the
params-blind `validate()` seam) it can raise `SparqlError`, so it is wrapped in
try/except → `_failure_outcome`, mirroring the original first-attempt / repair-loop
guarding. This is work-item 2 (re-point + mapping) plus work-item 3's assembly +
documentation half.

Purpose: This is the behavior-preserving refactor that makes engine-side SOTA
(few-shot / dense retrieval, Phase 7) reachable from SPARQL and inheritable by
Cypher. The definition of done is that NOTHING observable moves: scripted eval
pass-rate stays exactly 0.8333 with identical per-case verdicts, the transpiler is
untouched, W3C stays >= 96.4%, and the existing suite (including
`test_pipeline.py`'s happy/repair/exhaustion/transport/explain assertions) stays
green — AND no new crash path is introduced (params-driven errors on the final
re-translate degrade gracefully).

Output: `NlPipeline.run()` driving the shared engine; `explain()` /
`_translate_only` / `_call_llm_raw` preserved; the guarded re-translate; the
cost/audit decision documented (Success Criterion 6).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM output → deterministic transpiler | LLM-generated SPARQL enters `api.translate` via the `validate` seam AND via the final re-translate — same parser/visitor guards as the shipped `/translate` route |
| provider bridge → NLQueryEngine loop | provider responses + a re-raised transport exception cross into the engine loop and back into run() |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.1-RT | Tampering | re-translate of NLResult.query in run() | mitigate | The re-translate calls the SAME `api.translate` the `validate` seam already ran, against the SAME `self.resolver` the adapter was built with; it is a deterministic second pass over already-validated SPARQL. Because it additionally passes `params` (which validate() omits), it is wrapped in try/except SparqlError → `_failure_outcome`, so a params-driven error degrades to a graceful 422-shaped outcome rather than an uncaught crash. No new parsing surface, no new input origin. |
| T-06.1-DOS | Denial of Service / cost | NLQueryEngine retry loop | mitigate | `max_retries` is bound to the existing `max_repairs` (default 2, ceiling 5 via RepairLoop). A transport exception is re-raised by the bridge and terminates run() after ONE call (no silent retry storm). |
| T-06.1-NET | Information Disclosure | scripted eval / CI gate | mitigate | The CI gate runs the `scripted` config only — no network, no API key. Live-model runs are non-gating. Records carry codes + token counts, never request/response bodies. |
| T-06.1-VAL | Elevation / bypass | /nl-explain path | accept | `explain()` is deliberately NOT routed through the engine (RESEARCH work-item 4); its SPARQL-only path still runs the deterministic translator directly, so no guardrail is bypassed by the re-point. |
</threat_model>
