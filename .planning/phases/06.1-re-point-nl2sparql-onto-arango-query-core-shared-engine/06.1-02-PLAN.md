<objective>
Build the two adapter pieces the re-point needs, as a new module
`arango_sparql/nl2sparql/engine_adapter.py`:

1. `EngineProviderBridge` — adapts our `nl2sparql.client.LLMClient`
   (`generate(messages) -> LLMResponse`) to the engine's
   `arango_query_core.nl.providers.LLMProvider` protocol
   (`generate(system, user) -> (content, usage_dict)`), AND owns per-call
   `LLMCallRecord` accounting (work-item 3: cost/audit, option (b) — the bridge
   records per call, reading `provider`/`model` off the wrapped client and cost via
   `estimate_llm_cost_usd`).
2. `SparqlAdapter` — implements all 5 seams of
   `arango_query_core.nl.seams.QueryLanguageAdapter`, mapping each onto shipped
   nl2sparql/transpiler pieces exactly as the spike proved. Its constructor takes
   the caller's already-built `resolver: SchemaResolver` (in production the pipeline's
   `self.resolver`) which `validate()` uses, and a SEPARATE `ontology_ttl: str` used
   ONLY to embed the Turtle text into `grammar_prompt_section`. The two are decoupled
   because a mapping-JSON / analyzer-enriched request populates the resolver while
   leaving `ontology_ttl` empty — rebuilding a resolver from `ontology_ttl` inside
   `validate()` would drive the engine's accept/reject loop against the WRONG (empty)
   schema and diverge from the pipeline's final re-translate.

Purpose: These are the language-specific + accounting seams the engine cannot know.
Wave 3 wires them into `NlPipeline.run()`. Isolating them here (own file, own tests)
lets the verdict-reproduction, record-accounting, AND resolver-parity invariants be
proven BEFORE the pipeline is re-pointed. Covers work-items 1 and 3 (mechanism) from
`06.1-RESEARCH.md`.

Output: `engine_adapter.py` (bridge + adapter) and `test_engine_adapter.py`
reproducing the spike's 6-verdict result, asserting record accounting, and proving
`validate()` uses the injected resolver (not `ontology_ttl`).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM output → deterministic transpiler | LLM-generated SPARQL crosses into `api.translate` via the `validate` seam (untrusted text parsed by rdflib + visited by the transpiler) |
| wrapped LLMClient → provider bridge | provider responses (content + usage) enter the bridge |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.1-VAL | Tampering | SparqlAdapter.validate → api.translate | accept | The LLM-output→transpiler boundary is UNCHANGED by the re-point: `validate` calls the same `api.translate` (same parser/visitor guards, UnsupportedSparqlError surfacing) the shipped pipeline already used, now against the INJECTED resolver so it matches the pipeline's own schema. No new parsing surface; existing transpiler mitigations hold. |
| T-06.1-INF | Information Disclosure | repair_hint / LLMCallRecord.error | accept | repair_hint reuses `format_repair_context`, which already length-bounds error text (600-char cap); records carry no request/response bodies (rule: no bodies in logs), only codes + token counts. Behavior identical to current pipeline. |
| T-06.1-NET | Denial of Service / cost | EngineProviderBridge | mitigate | Tests use ScriptedLLMClient only (no network, no API key). The bridge adds no new outbound calls beyond what the wrapped client already makes; retry budget is bounded by the engine's `max_retries` (== max_repairs). |
</threat_model>
