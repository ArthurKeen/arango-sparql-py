## Verified interfaces (read from installed `arango-query-core` 0.1.0)

- **Engine loop** — `arango_query_core.nl.engine.NLQueryEngine(provider, adapter, few_shot_k=3, max_retries=2, guardrail_context={})`; `.generate(question, *, schema_context="") -> NLResult`. Owns generate→validate→repair + token accounting; strips code fences via `_strip_code_fence(content, language)`.
- **`NLResult`** fields: `query`, `ok`, `error`, `retries`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `cached_tokens`, `guardrail`, `validation`. **Note: no `aql`/`bind_vars`** — the engine only knows "valid/not," not the transpiler output.
- **Provider protocol** — `arango_query_core.nl.providers.LLMProvider.generate(system: str, user: str) -> (content, usage_dict)`. **Differs from our** `client.LLMClient.generate(messages) -> LLMResponse` → needs a ~5-line bridge.
- **Seam protocol** — `arango_query_core.nl.seams.QueryLanguageAdapter` (5 methods): `grammar_prompt_section(schema_context)`, `few_shot_index() -> FewShotIndex|None`, `validate(query) -> ValidationResult(ok, error, code)`, `repair_hint(query, failure) -> str`, `guardrails(query, context) -> GuardrailVerdict(allowed, reasons)`.
- **Few-shot** — `arango_query_core.nl.fewshot.FewShotIndex` (BM25 built-in) already exists; return `None` for behavior-preservation this phase (Phase 7 populates it).

## Seam → shipped-piece mapping (proven in spike)

| Seam | Maps to |
|------|---------|
| `grammar_prompt_section` | `nl2sparql.prompt._SYSTEM_PROMPT` + ontology Turtle |
| `few_shot_index` | `None` (zero-shot; Phase 7 wires the corpus) |
| `validate` | `arango_sparql.api.translate(query, resolver=...)` → ok / `SparqlError`→`(ok=False, code)` |
| `repair_hint` | the translator error string (mirrors `_REPAIR_USER_SUFFIX`) |
| `guardrails` | allow-all (no tenant/write-op checks yet) |

Provider bridge: wrap our `LLMClient` (incl. `ScriptedLLMClient`) so `(system,user)` → `[{system},{user}]` → `client.generate(...)` → `(resp.content, usage)`.

## Work-items the spike surfaced (MUST be in the plan)

1. **`NLResult` → `PipelineOutcome` mapping.** The `validate()` seam discards the `TranslateResult`, so `NLResult` carries no `aql`/`bind_vars`. After `engine.generate()`, **re-translate the final `result.query` once** (deterministic, cheap) to recover `aql`/`bind_vars` for `PipelineOutcome`. Preserve public fields: `nl, sparql, aql, bind_vars, warnings, llm_call_records, latency_ms, repaired`.
2. **Cost / audit accounting.** Our pipeline builds per-call `LLMCallRecord` + `estimate_llm_cost_usd`; the engine only accumulates token totals in `NLResult`. Decide: (a) reconstruct a coarse single `LLMCallRecord` from `NLResult` token totals, or (b) have the provider-bridge record per-call. Document whichever is chosen (success criterion 6).
3. **Fence extraction + repair wording differ.** Engine `_strip_code_fence` / its retry prompt ≠ our `extract_sparql_from_response` / `_REPAIR_USER_SUFFIX`. Identical on the scripted corpus; could shift **live-model** behavior. Add a live-provider before/after check as a non-gating task (RUN_EVAL live is gated), or explicitly accept.
4. **`/nl-explain` stays in `nl2sparql`.** The engine only does `generate`; keep `explain()` / `build_explain_messages` as-is (it doesn't route through `NLQueryEngine`).
