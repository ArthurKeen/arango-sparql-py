# Phase 07.1: Code Review Report

**Reviewed:** 2026-07-22T21:28:29Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

Reviewed the NL→SPARQL eval harness changes plus the two new vendored-dataset
converters (QALD-9-plus and CK25). All converters correctly use the mandated
`rdflib`-based `parse_sparql` + `SchemaResolver` + `translate()` stack rather
than hand-rolled validators (CLAUDE.md hard rules 1/3 satisfied), and both use
`yaml.safe_load`/`safe_dump` only. No blockers found.

**The two executor-flagged changes are both sound:**

1. **`runner.py` BNode canonicalization** — `_skeleton`/`_alpha_normalize`
   extending alpha-renaming to `BNode` is correct and does NOT mask genuine
   differences. `Variable` canonicalizes to `Variable("v{n}")` and `BNode` to
   `BNode("b{n}")`, which are distinct rdflib types with distinct `repr()`, so a
   candidate that substitutes a named variable where the gold uses a blank node
   (or vice versa) will NOT collide. Blank-node co-reference is preserved by
   applying a single shared bijection across the whole tree. The change is
   necessary: without it, `_canonical(same_string)` would not equal itself
   across two parses because rdflib mints a fresh skolem id per parse. The one
   residual concern (over-strictness) is filed as WR-04 below, and an ordering
   fragility that predates this change but is now extended to BNodes is WR-03.

2. **`test_eval.py` `==` → `<=` relaxation** — sound. The test is a purely
   structural, no-network validation of the checked-in `baseline.json`; it does
   not execute anything, so it cannot hide a runtime regression. Runtime
   per-case regressions are gated separately by
   `test_scripted_pass_rate_meets_baseline` over the `scripted` config. The
   relaxation still catches a *phantom* (`extra`) case in the live companion
   (`set(cfg.cases) - scripted_cases`), only permitting the documented and
   expected *missing* case (a corpus case added after the sha-pinned manual live
   sweep). `corpus_sha` pins provenance. Correct.

The findings below are quality/robustness defects, none of which block the phase.

## Warnings

### WR-01: QALD converter shares a mutable resolver across all queries, contradicting the CK25 converter's own documented safety rule

**File:** `tests/nl2sparql/eval/vendored/qald9plus/convert_qald.py:212` (and `:244`, `:407`)
**Issue:** `_BOOTSTRAP_RESOLVER` is a **module-level singleton** reused for every
one of the ~558 provisional-pass `translate()` calls, and `_final_survivors`
reuses one `final_resolver` across all survivors. This directly contradicts the
sibling CK25 converter, which deliberately builds a **fresh resolver per
question** with an explicit rationale (`convert_ck25.py:202-204`):

> "resolvers cache resolution results, and translate() may mutate
> resolver.warnings; a fresh instance per question keeps the filter's
> per-question outcome independent."

The concern is real and verifiable: `SchemaResolver` holds instance state
(`_class_cache`, `_property_cache`, `warnings`, and a `_warned_keys` dedup set —
`resolver.py:265-266,273,585`), and `translate()` folds `list(resolver.warnings)`
into every result (`api.py:97`). Because `_warned_keys` dedups by `(code, iri)`
for the *lifetime of the resolver*, a schema advisory emitted for query N is
silently suppressed for queries N+1…558, so `result.warnings` becomes
order-dependent and cross-contaminated. The module-level resolver also *persists
across `convert()` invocations in the same process*, so the run-2 resolver in
`test_two_runs_produce_identical_case_count_and_names` is pre-warmed by run 1 —
that determinism test only compares kept-name *sets* and would not detect
warning/cache divergence.

Keep/drop decisions key only on `result.aql` truthiness and `SparqlError`
(context-free, idempotent per IRI), so the survivor set is correct *today*, which
is why this is a WARNING and not a blocker. But it is latent fragility, an
unbounded-growth `warnings` list, and a direct violation of CLAUDE.md rule 4
("mirror the sibling's structure"; the two converters diverge on the exact point
CK25 flags as unsafe).

**Fix:** Build a fresh resolver per query in both passes, mirroring CK25:
```python
# provisional pass
resolver = SchemaResolver.from_turtle("", permissive_class_resolution=True)
result = translate(gold, resolver=resolver)
...
# final pass
for survivor in survivors:
    final_resolver = SchemaResolver.from_turtle(ontology_ttl)
    result = translate(survivor["expected"], resolver=final_resolver)
```
Drop the module-level `_BOOTSTRAP_RESOLVER`.

### WR-02: `convert_ck25` monkeypatches PyYAML's global `SafeRepresenter` at import time

**File:** `tests/nl2sparql/eval/vendored/ck25/convert_ck25.py:246`
**Issue:** `yaml.representer.SafeRepresenter.add_representer(str, _str_presenter)`
runs at **module import**, mutating a process-global class. Because the test
suite (and pytest collection) imports this module, every subsequent
`yaml.safe_dump` call *anywhere in the process* — including `convert_qald.main`'s
corpus dump and any other harness code — silently switches multi-line `str`
serialization to block-literal style. This is an import-time side effect with
process-wide reach and unpredictable ordering (the effect depends on whether
`convert_ck25` was imported first). PyYAML safely falls back to quoted style when
block style is invalid, so this does not corrupt data, but it is hidden global
state coupling and can make `convert_qald`'s output style (and the
`test_committed_*_matches_regenerated_output` drift guards) depend on import
order.
**Fix:** Scope the representer to a private `yaml.Dumper` subclass and pass it
explicitly, instead of mutating the shared `SafeRepresenter`:
```python
class _BlockDumper(yaml.SafeDumper):
    pass
_BlockDumper.add_representer(str, _str_presenter)
# in write_corpus:
path.write_text(yaml.dump(corpus, Dumper=_BlockDumper, sort_keys=False,
                          allow_unicode=True, width=100))
```

### WR-03: alpha-numbering can fall back to hash-seed iteration order for set-first-occurrence identifiers

**File:** `tests/nl2sparql/eval/runner.py:257-269` (`_skeleton`), `:296-318` (`_alpha_normalize`)
**Issue:** `_skeleton` erases every `Variable` to the constant `"?"` and every
`BNode` to the constant `"?_bnode"`. When `_alpha_normalize` orders a
`set`/`frozenset` via `sorted(node, key=_skeleton)`, a set composed entirely of
variables (e.g. an rdflib `_vars` frozenset) or entirely of blank nodes yields an
all-identical key — a total tie — so `sorted` preserves the set's native
iteration order, which is `PYTHONHASHSEED`-dependent for `Identifier` objects. If
an identifier's *first* occurrence in the walk is inside such a tied set, its
canonical `v{n}`/`b{n}` number is assigned in hash-seed order, making
`_canonical` non-deterministic *across processes*. This is masked today only
because identifiers virtually always first appear in an **ordered** structure
(`BGP.triples`/`PV` are lists) before any `_vars` frozenset, and because the
judge compares two canonicalizations *within a single process* (shared seed).
The BNode extension (this phase) inherits the same fragility. It is not
currently triggerable by the checked-in golds, hence WARNING.
**Fix:** Make the skeleton ordering fully structural by seeding numbering only
from ordered structures, or break set ties deterministically — e.g. tag each
`Variable`/`BNode` skeleton with a stable structural discriminator, or assert
that every identifier is mapped before any set containing it is ordered. At
minimum, add a cross-seed determinism test
(`PYTHONHASHSEED` sweep asserting `_canonical(s) == _canonical(s)` across
subprocess runs for a gold with a blank node).

### WR-04: canonical judge treats a blank node as non-equivalent to a named variable, under-crediting semantically-equivalent candidates

**File:** `tests/nl2sparql/eval/runner.py:296-303`, `:329-336` (`_judge_canonical`)
**Issue:** A blank node in a SPARQL graph pattern is semantically an existential
(non-distinguished) variable. A model output like `SELECT ?x { ?x :p ?y }` is
SPARQL-equivalent to a gold `SELECT ?x { ?x :p [] }`, but because `BNode`
canonicalizes to `BNode("b{n}")` and a `Variable` to `Variable("v{n}")`, the
judge scores them as different. This does NOT hide regressions (it is
conservative/over-strict), but it can *deflate* the measured pass rate and
penalize a correct model, which reduces the signal the eval is meant to measure
for a Phase-7 lift.
**Fix:** If alpha-equivalence up to blank-node/variable interchange is desired,
normalize non-distinguished blank nodes and non-projected join variables to the
same canonical class; if the strictness is intentional, document it explicitly in
`_judge_canonical` so a future reader does not "fix" it as a bug.

### WR-05: CK25 `convert_case` raises `KeyError` on a malformed question instead of a logged drop, inconsistent with QALD's graceful handling

**File:** `tests/nl2sparql/eval/vendored/ck25/convert_ck25.py:164-170`
**Issue:** `convert_case` unconditionally reads `question["question"]["en"]` and
`question["query"]["sparql"]`. A question missing an `en` string (or the
`sparql` field) raises `KeyError`, aborting the entire conversion. The QALD
sibling handles the analogous case gracefully by dropping with a
`no-english-string` reason (`convert_qald.py:230-233`), and this converter's own
"no silent truncation" contract (`filter_cases` docstring) is defeated by an
uncaught exception that discards *all* progress. CK25's curated raw data makes
this unlikely today, hence WARNING.
**Fix:** Guard missing fields in `filter_cases` and record them as a dropped
reason (e.g. `"missing question.en or query.sparql"`) rather than letting the
`KeyError` propagate, matching the QALD `no-english-string` bucket.

## Info

### IN-01: CK25 collection-name pluralization is naïve and collision-prone

**File:** `tests/nl2sparql/eval/vendored/ck25/convert_ck25.py:122`
**Issue:** `collection_name = local_name if local_name.endswith("s") else f"{local_name}s"`
produces incorrect English plurals (`Company` → `Companys`) and can collide two
distinct classes onto one physical name. This is cosmetic for the canonical
(algebra) judge — the mapped collection *string* never enters algebra comparison
— so it only matters if execution-tier judging is ever run against real data for
CK25.
**Fix:** If the physical name is purely nominal, drop the pluralization and use
`local_name` verbatim (as the QALD converter effectively does via
`_disambiguated_names`); otherwise add collision detection.

### IN-02: `power.py` raises bare `KeyError` for unsupported `alpha`/`power` values

**File:** `tests/nl2sparql/eval/power.py:35-36`, `:47-48`
**Issue:** `_Z[alpha]` / `_Z_BETA[power]` raise an unlabeled `KeyError` when
called with an `alpha`/`power` outside the small hardcoded z-tables (e.g.
`alpha=0.01`). Callers get no hint of which value is unsupported.
**Fix:** Wrap the lookups with a clear error, e.g.
`if alpha not in _Z: raise ValueError(f"unsupported alpha {alpha!r}; supported: {sorted(_Z)}")`.
