# Phase 07.1: NL→SPARQL eval via public benchmarks - Context

**Gathered:** 2026-07-22
**Status:** Ready for planning
**Supersedes:** the original "synthetic eval-corpus growth" approach for this phase. After a
`/grill-me` design review (2026-07-22), the synthetic-generation plan was **retired** in favor
of adopting public NL→SPARQL benchmarks. Rationale is captured in the decisions below; the
prior synthetic decisions (old D-01..D-11) are void. The phase directory slug is legacy — the
phase is now "NL→SPARQL eval via public benchmarks." Phase 07.2 (CK25 anchor) is **folded into
this phase**.

<domain>
## Phase Boundary

Make NL→SPARQL translation quality **measurable with real statistical power** by **adopting
public, human-authored NL→SPARQL benchmark test sets** — not by generating a synthetic corpus.
The eval judge already compares SPARQL-to-SPARQL (canonical algebra; no data or transpiler
needed for positive cases), so public (question → gold-SPARQL) sets drop into the existing
harness cheaply. This gets the eval to ~5–8pt minimum-detectable-effect (from ~16pt at 25
cases) using real, independently-vetted questions — while eliminating the correctness,
external-validity, and SPARQL-fluency risks of synthetic generation.

**In scope:**
- Adopt **QALD-9-plus** (DBpedia, CC-BY-4.0, ~408+150 English Q with gold SPARQL) as the
  **powered capability gate**.
- Adopt **CK25** (corporate/product KG, CC-BY-4.0, ~50 expert-curated Q→gold-SPARQL) as the
  **corporate-domain relevance anchor** (directional).
- Author a **small refusal supplement** (~a dozen `expect_refusal` cases) matched to the
  transpiler's actual coverage — the one thing public sets can't provide.
- Keep/reuse the **power-analysis module** to report achieved MDE on each adopted set.
- Wire both sets into the existing harness (schema load + question filter + `configs.yml`),
  regenerate the scripted baseline, and keep the W3C ≥96.4% non-regression guard.

**Explicitly OUT of scope (retired or deferred):**
- **The synthetic generator is retired** (templates / enumeration / LLM NL-authoring /
  faithfulness judge / partitioning). Not built. Revisited only if real QALD+CK25 numbers show
  a specific need for more *corporate-domain* power — then as an amplifier of CK25's real
  patterns, never a generic toy schema.
- v1.1 levers unchanged: generator fine-tuning (SFT/LoRA), execution-guided selection,
  embedder/hybrid-retrieval swap.
- Grounding the eval in a live/evolving CDF or specific-customer schema.

**Non-regression (hard invariants):** deterministic SPARQL→AQL transpiler untouched; W3C DAWG
query-eval coverage ≥ 96.4%; `scripted` stays the no-network CI default; live/credentialed
sweeps stay gated + human-run + human-folded; no secrets committed.
</domain>

<decisions>
## Implementation Decisions

### Approach (the pivot)
- **D-01: Adopt public benchmarks; do NOT build a synthetic generator.** The eval judge is
  SPARQL-vs-SPARQL canonical algebra (`runner._judge_canonical`, `runner.py:310-317`) — it
  needs neither the transpiler-to-AQL nor a live data endpoint for positive cases. So a public
  (question → gold-SPARQL) set is adopted by: loading its schema so the pipeline can generate
  against it → running the pipeline → comparing generated-SPARQL algebra to the gold. This
  delivers power with real, pre-vetted questions and removes the template-correctness,
  external-validity, and SPARQL-fluency risks that sank the synthetic plan.

### Which sets, and their roles
- **D-02: QALD-9-plus = the powered capability gate.** DBpedia, human-readable IDs, CC-BY-4.0,
  ~408 train + 150 test English questions with gold SPARQL (QALD-JSON). Enough volume for
  ~6–8pt MDE — near the ≤5pt goal, for free. Measures general SPARQL-generation *skill* (right
  predicates, OPTIONAL/aggregation/paths), which transfers across schemas better than absolute
  pass-rates. Pull in **LC-QuAD 1.0** (DBpedia, ~5k) later ONLY if tighter than ~5pt is needed.
- **D-03: CK25 = the corporate-domain relevance anchor.** `github.com/eccenca/ck25-dataset`,
  CC-BY-4.0, ~50 expert-curated corporate/product Q→gold-SPARQL (→ ~30–45 after feature
  filtering). Ships a small Turtle ontology + instance data. **Directional** check that the
  translator is strong on corporate-schema questions, not just DBpedia trivia — NOT a power
  gate (too small; that's fine for an anchor). Domain-matched to the Contextual Data Fabric
  goal. (This is the folded-in former Phase 07.2.)
- **D-04: Small hand-authored refusal supplement.** ~a dozen `expect_refusal` cases keyed to
  the transpiler's *actual* unsupported features (public sets don't provide these; refusal is
  transpiler-coupled — judged by `outcome.aql == ""`, `runner.py:341-349`). Retain the existing
  negatives. One-time SPARQL-fluent review covers this small set — negligible risk.

### Adaptation mechanics
- **D-05: Schema adaptation per set.** Load each set's ontology via the eval's `ontology:`
  mechanism (`SchemaResolver.from_turtle`). CK25 ships a small Turtle ontology (~13 classes /
  30 properties) — near drop-in; add `phys:` mapping annotations + map to an ArangoDB physical
  model. QALD-9-plus/DBpedia → **subset** the DBpedia ontology to the classes/properties the
  selected questions actually touch (don't load all of DBpedia).
- **D-06: Question filtering.** Keep a public question only if (a) its gold SPARQL parses via
  rdflib, (b) it is algebra-judgeable (and, for end-to-end coverage, transpiles), and (c) it
  uses only schema terms present in the loaded subset. Log how many are dropped and why — no
  silent truncation. Report the surviving N and its achieved MDE.
- **D-07: Keep the power-analysis module.** `required_n` / `achieved_mde` (pure-Python, no
  scipy, matching `runner.paired_mcnemar`) — the one salvage from the retired synthetic plan.
  Used to report the actual sensitivity on whatever set/subset is adopted, so MDE is always
  known and documented.

### Discipline & provenance
- **D-08: Licensing/attribution.** QALD-9-plus and CK25 are both **CC-BY-4.0** — vendor the
  adopted subsets into the eval area with their license notice + attribution (source repo +
  citation). This is distinct from the CLAUDE.md "no vendored W3C DAWG test data" rule (that
  concerns the W3C conformance suite specifically). No secrets committed.
- **D-09: CI discipline unchanged.** `scripted` stays the no-network CI default; live/model
  sweeps stay `RUN_EVAL=1` + key, human-run out-of-band, human-folded (Phase 06.2/07). New sets
  = new corpus files + `configs.yml` entries; **no runner surgery** (the harness is already
  model/set-agnostic).

### Claude's Discretion
- Exact QALD subset size after filtering; whether/when to add LC-QuAD for more volume.
- Number and exact content of refusal-supplement cases.
- `configs.yml` naming; how the vendored sets are laid out under `tests/nl2sparql/eval/`.
- The concrete DBpedia ontology subset for the QALD questions kept.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **The eval harness needs no new architecture.** Adopting a set = new corpus file(s) (in the
  existing `corpus.yml` shape: `ontology:` + `cases:` with `nl`/`expected`) + new `configs.yml`
  entries. The runner, judge, provider factory, and baseline machinery are already set-agnostic.
- **`_judge_canonical`** grades NL→SPARQL by comparing generated-SPARQL algebra to gold SPARQL —
  the reason public sets are cheap to adopt (no data/transpiler needed for positive cases).
- **`_judge_execution`** (pyoxigraph over a `data:` Turtle fixture) is available if a set ships
  data and result-based judging is wanted — more robust than algebra match where applicable.
- **`SchemaResolver.from_turtle`** ingests the adopted set's ontology directly (CK25 ships
  Turtle; DBpedia subset authored as Turtle).
- **Power-analysis module** (salvaged) reports achieved MDE per set/subset.

### Established Patterns
- Provenance (`corpus_sha` + model/temperature); gated-not-CI live sweep; committed-invariant
  tests (gold-must-parse, corpus-schema, headroom). Adopted sets slot into all of these.

### Integration Points
- New vendored dataset files + `configs.yml` entries under `tests/nl2sparql/eval/`.
- DBpedia-subset ontology + CK25 ontology authored/converted to the `ontology:` Turtle shape.
- Regenerated scripted `baseline.json`; W3C ≥96.4% guard unchanged.

</code_context>

<specifics>
## Specific Ideas

- **Why the pivot (grill-me conclusion):** the synthetic generator was over-built relative to
  adopting benchmarks the field already trusts. Public sets solve the *power* problem 07.1
  existed for (QALD-9-plus alone ≈ ~6–8pt MDE) while being real, comparable, and free of the
  template-correctness single-point-of-failure and external-validity drift.
- **Two jobs, two sets:** QALD-9-plus = *powered capability gate* (detects small regressions;
  measures transferable SPARQL skill). CK25 = *corporate-domain relevance anchor* (directional;
  guards against "good at trivia, bad at corporate schemas"). Both real; neither replaces the
  other.
- **Schema-dependence is the reason to keep CK25:** absolute pass-rates don't transfer across
  domains, so a corporate anchor is needed alongside the DBpedia gate to stay honest about the
  CDF-shaped target.
- **The only irreducible bespoke data** is the refusal supplement — "should refuse" cases are
  specific to *this* transpiler's coverage and no public set provides them.

</specifics>

<deferred>
## Deferred Ideas

- **Synthetic generation as a corporate-domain power amplifier** — build ONLY if real QALD+CK25
  numbers show CK25's ~40 cases can't give enough corporate-domain sensitivity; then amplify
  CK25's real patterns (real seed + real schema + real validity anchor), never a generic toy
  schema. This is the well-founded future home of the retired generator.
- **LC-QuAD 1.0** (DBpedia, ~5k) — extra volume if tighter than ~5pt MDE is ever needed.
- **Spider4SPARQL** — schema-diversity benchmark; larger adaptation cost; future breadth.
- **Live CDF / specific-customer schema eval** — the ultimate domain-matched target; deferred
  to avoid coupling a fixed regression gate to an evolving external artifact.
- v1.1 accuracy levers (SFT/LoRA, execution-guided selection, embedder/hybrid swap) — unchanged.

</deferred>
