## Summary

The existing harness (`tests/nl2sparql/eval/runner.py` + `corpus.yml` + `configs.yml`) needs
**no architectural change** to adopt public benchmarks — it already separates "which questions"
(a YAML `cases:` list, each carrying its own optional per-case `ontology:` override) from
"how they're judged" (`_judge_canonical`, pure SPARQL-vs-SPARQL algebra comparison, no data or
transpile needed for the gold side). QALD-9-plus and CK25 both ship exactly the shape this
harness wants: (English question, gold SPARQL) pairs, plus a schema artifact to build the
`ontology:` Turtle block from. **CK25's ontology is nearly drop-in** — `graphs/prod-inst.ttl`
already declares `owl:Class`/`owl:ObjectProperty` with `rdfs:domain`/`rdfs:range` axioms; only
`phys:collectionName`/`phys:edgeCollectionName` annotations need adding. **QALD-9-plus has no
shipped ontology** — DBpedia classes/properties are used directly by IRI in the gold queries,
so a **minimal Turtle subset must be authored** covering only the classes/properties the kept
questions touch (never the full DBpedia ontology).

One real, load-bearing gap exists between the CONTEXT's framing ("new corpus files, no runner
surgery") and the current code: `runner.py`'s `_load_corpus()` hardcodes a single `corpus.yml`
path. The clean fix — and the one genuinely additive change this phase needs — is a `corpus:`
key on each `configs.yml` entry (default: today's `corpus.yml`, unchanged), giving QALD and CK25
their **own separate runs/reports** rather than being merged into one blended pass-rate. This
matches D-02/D-03 exactly: QALD is the powered gate (its own MDE), CK25 is the anchor (its own,
un-gated number) — they should never share one aggregate pass_rate.

The transpiler's error-surfacing is more permissive than a naive read of `UnsupportedSparqlError`
suggests: an **undeclared** property (not present in the ontology at all) degrades gracefully to
an attribute lookup with a warning — it does NOT raise. Only a property *explicitly declared*
`owl:ObjectProperty` **without** `phys:edgeCollectionName`, or a class used in `?x a :Class`
that isn't declared `owl:Class` at all (with `permissive_class_resolution` off, the harness's
default), raises. This means D-06's filter criterion (c) — "uses only schema terms present in the
subset" — is really about the **ontology being a faithful/complete-enough in-context schema for
the LLM to generate matching SPARQL**, not primarily about avoiding transpiler exceptions on the
gold side (the gold's transpilability gate, `test_gold_transpilable.py`, is separately enforced
and is what actually filters).

**Primary recommendation:** Author a `corpus:`-key-aware `_load_corpus(path)` (the one additive
runner change), vendor QALD-9-plus (English DBpedia, train+test combined = ~558 raw) and CK25
(~50 raw) under `tests/nl2sparql/eval/vendored/{qald9plus,ck25}/` each with a conversion script,
an authored `phys:`-annotated ontology subset, a filter log, and CC-BY-4.0 NOTICE — then wire two
new `configs.yml` entries per set (scripted + live) and regenerate `baseline.json`.

### Pattern 1: The additive `corpus:` config key (THE mechanism, not a re-architecture)

**What:** `configs.yml` gains an optional `corpus:` key (a path relative to `EVAL_DIR`); `run()`
threads it through to `_load_corpus`. Absent `corpus:` == today's `corpus.yml` — byte-identical
behavior for every existing config.

**When to use:** Every time a new vendored set needs its own report/pass-rate/MDE, distinct from
the hand-authored corpus and from each other (D-02/D-03's "two jobs, two sets" requirement).

**Example:**
```python
# Source: proposed additive change to tests/nl2sparql/eval/runner.py,
# mirroring the precedent already set by the `few_shot:` config-key addition
# (README: "absent `few_shot:` == today's zero-shot behavior").

def _load_corpus(path: Path = CORPUS_PATH) -> dict[str, Any]:
    corpus = yaml.safe_load(path.read_text())
    for case in corpus.get("cases", []):
        CorpusCase(**case)
    return corpus

def run(config_name: str) -> Report:
    configs = _load_configs()["configs"]
    config = configs[config_name]
    corpus_path = EVAL_DIR / config.get("corpus", "corpus.yml")
    corpus = _load_corpus(corpus_path)
    ...  # everything below this line is UNCHANGED
```

```yaml
# configs.yml — new entries, same shape as existing ones + one new key
scripted-qald9plus:
  provider: {type: scripted}
  judge: canonical
  max_repairs: 2
  corpus: vendored/qald9plus/corpus.yml

scripted-ck25:
  provider: {type: scripted}
  judge: canonical
  max_repairs: 2
  corpus: vendored/ck25/corpus.yml

openai-gpt4o-mini-qald9plus:

```

This is the **only** code change to `runner.py` this phase needs. It does not touch
`_judge_canonical`, `_judge`, `_client_for`, the paired-analysis helpers, or `write_report` —
satisfying D-09's "no runner surgery" in the sense that matters (the judge/pipeline logic is
untouched); it is data-plumbing in the exact spirit of the already-shipped `few_shot:` key.

### Pattern 2: QALD-9-plus JSON → corpus case conversion

**What:** QALD-JSON's structure `[VERIFIED: fetched directly from
raw.githubusercontent.com/KGQA/QALD_9_plus/main/data/qald_9_plus_test_dbpedia.json]`:

```json
{
  "questions": [
    {
      "id": "99",
      "question": [
        {"language": "en", "string": "What is the time zone of Salt Lake City?"},
        {"language": "de", "string": "..."}
      ],
      "query": {
        "sparql": "PREFIX res: <http://dbpedia.org/resource/> PREFIX dbp: <http://dbpedia.org/property/> SELECT DISTINCT ?uri WHERE { res:Salt_Lake_City <http://dbpedia.org/ontology/timeZone> ?uri }"
      },
      "answers": [ { "head": {"vars": ["uri"]}, "results": {"bindings": [...] } } ]
    }
  ]
}
```

File names `[VERIFIED: fetched from github.com/KGQA/QALD_9_plus/tree/main/data]`:
`data/qald_9_plus_train_dbpedia.json`, `data/qald_9_plus_test_dbpedia.json` (also
`_wikidata` variants — NOT used, per D-02 DBpedia-only scope).

**Example (conversion sketch):**
```python
# Source: proposed conversion script (tests/nl2sparql/eval/vendored/qald9plus/convert_qald.py)
import json

def convert(json_path: str) -> list[dict]:
    raw = json.loads(open(json_path).read())
    cases = []
    for q in raw["questions"]:
        en = [v["string"] for v in q["question"] if v["language"] == "en"]
        if not en:
            continue  # some entries may lack an English string; skip, log it
        sparql = q["query"]["sparql"]
        cases.append({
            "name": f"qald9plus-{q['id']}",
            "nl": en[0],
            "expected": sparql,
        })
    return cases
```

Two English DBpedia files (`train` + `test`) should both feed the corpus — D-02's "~6-8pt MDE"
estimate assumes the **combined** ~558-question pool (see §"Power/MDE" below for why: at
N=150 alone the achieved MDE is ~11pt, not the ~6-8pt CONTEXT cites; only the combined train+test
pool reaches that range).

**Note on `dct:`/`dbc:` prefixes (Question 2 in the fetched sample):** not every QALD gold uses
`dbo:`/`dbp:` predicates — some use `dct:subject` against a `dbc:Category:` resource. The
authored ontology subset must declare the classes/properties actually referenced, whatever
namespace they come from — grep every kept gold's triples for `URIRef` predicates/objects-in-
type-position, don't assume `dbo:`-only.

### Pattern 3: CK25 questions.yml → corpus case conversion + ontology extraction

**What:** CK25's YAML structure `[VERIFIED: fetched directly from
raw.githubusercontent.com/eccenca/ck25-dataset/main/questions.yml]`:

```yaml
dataset:
  id: https://text2sparql.aksw.org/2025/corporate/
  prefix: ck25
  defaultNamespace: http://ld.company.org/prod-vocab/

questions:
  - id: 1
    question:
      en: In which department is Ms. Brant?
    features: [SELECT]
    classes: [":Department", ":Employee"]
    properties: [":memberOf"]
    query:
      sparql: |
        PREFIX pv: <http://ld.company.org/prod-vocab/>
        SELECT DISTINCT ?result
        WHERE {
          <http://ld.company.org/prod-instances/empl-Karen.Brant%40company.org> pv:memberOf ?result .
          ?result a pv:Department .
        }
```

CK25's gold queries characteristically use a **constant instance IRI as subject** (e.g. the
literal `<http://ld.company.org/prod-instances/empl-Karen.Brant%40company.org>`), not a bound
variable with a separate `?x a :Class` triple — confirmed transpilable: constant-`URIRef`-subject
triples are a supported code path (`arango_sparql/translate/visitor.py:1616-1621` binds the
subject-URI equality FILTER directly; `_triple_priority`, `visitor.py:2090-2114`, explicitly
documents "triples whose subject is a URI" as priority tier 2, always opens a fresh `FOR`).

**Ontology source `[VERIFIED: fetched directly from
raw.githubusercontent.com/eccenca/ck25-dataset/main/graphs/prod-inst.ttl]`:** the schema is
embedded directly in `graphs/prod-inst.ttl` (a hybrid schema+instance file, NOT a separate
ontology-only file) — extract just the `owl:Class`/`owl:ObjectProperty`/`owl:DatatypeProperty`
declarations with their `rdfs:domain`/`rdfs:range` axioms, discard the instance triples:

```turtle
# Confirmed present in graphs/prod-inst.ttl (schema portion), namespace pv: = http://ld.company.org/prod-vocab/
pv:Agent a owl:Class .
pv:Employee a owl:Class .
pv:Manager a owl:Class .
pv:Product a owl:Class .
pv:memberOf a owl:ObjectProperty ; rdfs:domain pv:Agent ; rdfs:range pv:Department .
pv:hasManager a owl:ObjectProperty ; rdfs:domain pv:Employee ; rdfs:range pv:Manager .
```

**Annotate with `phys:` (the ONLY genuinely new authoring this set needs):**
```turtle
@prefix phys: <http://arangodb.com/schema/physical#> .
pv:Employee a owl:Class ; phys:collectionName "Employees" .
pv:Department a owl:Class ; phys:collectionName "Departments" .
pv:memberOf a owl:ObjectProperty ; rdfs:domain pv:Agent ; rdfs:range pv:Department ;
  phys:edgeCollectionName "memberOf" .
```

**When to use:** For every CK25 class/property the kept questions' `classes:`/`properties:`
fields reference (these fields are a built-in per-question feature manifest — use them directly
to drive which schema terms need `phys:` annotation, rather than re-deriving usage from the
SPARQL text).

### Pattern 4: The graceful-degradation resolver contract (why the filter is about LLM context, not just transpile-errors)

**What:** `SchemaResolver.resolve_property` (`resolver.py:501-529`) treats ANY property IRI not
declared `owl:ObjectProperty`/`owl:DatatypeProperty` in the ontology as an **attribute fallback
with a warning** — it never raises. `resolve_class` (`resolver.py:395-433`) DOES raise
`SchemaResolutionError` for an undeclared class used in `?x a :Class`, unless
`permissive_class_resolution=True` is passed to `from_turtle` (default `False`).

**When to use:** This means the D-06 filter's criterion (c) — "uses only schema terms present in
the subset" — matters most for **classes** (a real hard-fail point) and matters for
**properties** primarily so the ontology text fed into the LLM's prompt (`ontology_ttl=`) is a
faithful, complete schema surface for the *model* to generate against — not because an omitted
property IRI would itself break the gold's `translate()` call.

**Anti-pattern to avoid:** Assuming `rdfs:domain` declarations on properties functionally route
subject-collection selection at translate time. **They do not** — `ResolvedProperty.domain_iri`
is populated by `resolve_property` but is `[VERIFIED: codebase — grep for "domain_iri" across
arango_sparql/ returns zero consumers outside resolver.py]` **never read by the visitor.**
Domain/range axioms are valuable as human/LLM-readable documentation (matching the existing
`corpus.yml` authoring convention) but do not change transpile behavior. Do not over-invest
effort trying to get every DBpedia property's domain "just right" for functional correctness —
get it right for LLM-context faithfulness instead.

### Anti-Patterns to Avoid
- **Merging QALD + CK25 + hand-authored cases into one blended `pass_rate`.** D-02/D-03 are
  explicit that these are two DIFFERENT jobs (powered gate vs. directional anchor) — report them
  as separate `baseline.json` entries with separate `achieved_mde` values, never averaged.
- **Loading the full DBpedia ontology** to avoid authoring a subset. CONTEXT D-05 explicitly
  forbids this; it also defeats the purpose of an auditable "what schema does the model see"
  surface and would make `SchemaResolver.from_turtle` parse an enormous, mostly-irrelevant graph
  on every case (`SchemaResolver.from_turtle` is called once per case inside `run()`'s loop,
  `runner.py:395` — a large ontology means re-parsing a large Turtle graph N times per sweep).
- **Silently dropping QALD questions that fail to parse/transpile** without logging why (D-06
  explicitly requires "no silent truncation" — write a `filter_log.md` per set).
- **Treating CK25's small N as if it should hit `p < 0.05`** on any comparison — its role is
  directional (D-03); do not gate CI or promotion decisions on a CK25 McNemar p-value.

## Common Pitfalls

### Pitfall 1: The single-hardcoded-`corpus.yml` trap
**What goes wrong:** A planner reads CONTEXT D-09 ("new corpus files + configs.yml entries; no
runner surgery") and assumes zero code changes are needed, then discovers `_load_corpus()` always
reads the same `CORPUS_PATH` constant — QALD/CK25 cases silently never run because they're not
in `corpus.yml`.
**Why it happens:** The harness was built for a single, evolving hand-authored corpus; multi-set
support was never exercised before this phase.
**How to avoid:** Make the ONE additive change in Pattern 1 (`corpus:` config key,
default-preserving) at Wave 0, before authoring any vendored case content.
**Warning signs:** `RUN_EVAL=1 pytest -m eval` shows 0 QALD/CK25 cases executed despite the
vendored `corpus.yml` files existing on disk.

### Pitfall 2: Assuming `rdfs:domain` functionally matters (see Pattern 4)
**What goes wrong:** Spending disproportionate authoring effort getting every DBpedia property's
domain/range "correct" for transpile purposes, when the visitor never reads `domain_iri` at all.
**Why it happens:** The existing `corpus.yml`'s ontology block documents domain/range on every
property, giving the (false) impression it's functionally load-bearing.
**How to avoid:** Get domain/range right for LLM-prompt faithfulness (so the model's generated
SPARQL uses the correct predicates in the correct triple shape); don't treat it as a transpile
correctness requirement.
**Warning signs:** Debugging a "why didn't this transpile" failure by adjusting `rdfs:domain` —
the actual fix is almost always `phys:collectionName`/`phys:edgeCollectionName` presence, or
`?x a :Class` needing the class declared `owl:Class`.

### Pitfall 3: Merging QALD + CK25 into one blended report (see Anti-Patterns)
**What goes wrong:** A single combined `pass_rate`/`achieved_mde` masks the fact that QALD is the
statistically powered signal and CK25 is a small directional check — a regression hidden inside
CK25's ~40 cases would be invisible in a blended number dominated by QALD's ~300-500.
**Why it happens:** It is structurally easier to concatenate all cases into one `cases:` list
than to keep two separate configs/reports.
**How to avoid:** Two separate `configs.yml` entries (`scripted-qald9plus`, `scripted-ck25`), two
separate `baseline.json` top-level keys, two separate `achieved_mde` computations.
**Warning signs:** `baseline.json` has one new key covering all ~350-550 new cases instead of two.

### Pitfall 4: QALD-9's known noise floor
**What goes wrong:** A handful of QALD-9(-plus) gold queries are documented in the KGQA
literature as noisy/ambiguous/occasionally malformed (a long-recognized property of the QALD-9
benchmark, not specific to this repo). Treating 100% of the 558 raw questions as automatically
usable overstates the survivable N.
**Why it happens:** QALD-9-plus's improvement over QALD-9 was primarily *translation* quality
(adding 8 languages), not a full re-audit of the original QALD-9 English/DBpedia gold queries —
the underlying gold-query quality issues from QALD-9 largely carry over.
**How to avoid:** Run the full D-06 filter (parse + judgeable + subset-schema-only) and REPORT the
actual survival count and drop reasons — do not assume a specific percentage without measuring.
**Confidence:** MEDIUM — the existence of QALD-9 gold-quality issues is well-established
community knowledge `[CITED: general KGQA/QALD benchmark literature — not independently re-
verified against every individual QALD-9-plus gold query in this session]`; the EXACT survival
rate for this repo's specific transpiler feature set is unmeasured and must be established by
running the actual conversion + filter, not assumed from this research.

### Pitfall 5: Multiple English paraphrase strings per question
**What goes wrong:** QALD-9-plus's `question` array occasionally carries more than one entry for
the SAME language (seen for `de`/`ru`/`lt` in the fetched sample) — a naive converter that
assumes exactly one string per language could silently drop paraphrase variety, or (worse) pick
inconsistently across re-runs if iterating an unordered structure.
**Why it happens:** The dataset's own design supports multiple phrasings per question for
robustness testing; this repo doesn't need that for eval-corpus purposes (one canonical NL
question per gold is enough) but must handle it deterministically.
**How to avoid:** Explicitly take the FIRST `language == "en"` entry (deterministic, order-
preserving JSON parse) and log if more than one exists per question — one case per gold query,
not one case per paraphrase.
**Warning signs:** A conversion run producing a different case count on two separate runs against
the same input file.

## Code Examples

### Power-analysis module (D-07 salvage — verbatim carry-forward, no scipy)
```python
# Source: derived from Connor (1987) sample-size formula for McNemar's test,
# following the normal-approximation convention used by powerandsamplesize.com /
# PASS / pwrss documentation of the Connor family. Mirrors this repo's existing
# pure-Python stats convention (runner.paired_mcnemar / bootstrap_paired_delta
# deliberately avoid scipy). Carried forward unchanged from the retired
# synthetic-corpus research (same formula, same citation) per D-07.
from __future__ import annotations
import math

_Z = {
    0.05: 1.9600,   # two-sided alpha=0.05  -> z_{alpha/2}
    0.10: 1.6449,   # two-sided alpha=0.10  -> z_{alpha/2}
}
_Z_BETA = {
    0.70: 0.5244,
    0.80: 0.8416,
    0.90: 1.2816,
}


def required_n(mde: float, discordant_rate: float, *, alpha: float = 0.05, power: float = 0.80) -> int:
    """Minimum paired-case count N to detect a paired pass-rate delta >= `mde`
    at the given `alpha` (two-sided) and `power`, assuming a discordant-pair
    proportion of `discordant_rate` (Connor 1987 approximate formula)."""
    z_a = _Z[alpha]
    z_b = _Z_BETA[power]
    n = ((z_a + z_b) ** 2) * discordant_rate / (mde ** 2)
    return math.ceil(n)


def achieved_mde(n: int, discordant_rate: float, *, alpha: float = 0.05, power: float = 0.80) -> float:
    """Inverse of `required_n` — the minimum detectable effect actually
    achieved at case count `n` and an (observed or assumed) discordant rate."""
    z_a = _Z[alpha]
    z_b = _Z_BETA[power]
    return math.sqrt(((z_a + z_b) ** 2) * discordant_rate / n)
```

**Citation:** Connor, R.J. (1987). "Sample size for testing differences in proportions for the
paired-sample design." *Biometrics* 43(1):207-211. `[CITED: secondary sources
(powerandsamplesize.com/PASS/pwrss documentation summaries) — the primary 1987 Biometrics paper
was not independently re-fetched this session; arithmetic independently verified by hand against
this repo's own `paired_mcnemar` exact-test semantics in the prior research pass.]`
