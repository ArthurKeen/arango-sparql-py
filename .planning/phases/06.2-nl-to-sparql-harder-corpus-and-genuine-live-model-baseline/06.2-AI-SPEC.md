## 1. System Classification

**System Type:** Code Automation (NL→SPARQL semantic parsing) — **this phase (06.2) designs the *Evaluation* of that system**, not a new generator. The AI system under evaluation is the NL→SPARQL generator (`arango_query_core.nl.NLQueryEngine` driven through this repo's `SparqlAdapter`); Phase 06.2 hardens its measurement.

**Description:**
The NL→SPARQL generator turns an English question into a conceptual query serialized as SPARQL — the intermediate representation the Contextual Data Fabric decomposes and routes. It is the front door of the live federated-query path: if the SPARQL IR is wrong, every downstream stage faithfully returns a wrong (but cited) answer. Phase 06.2 does **not** change the generator. It replaces the 6 toy single-BGP scripted eval cases with a real-difficulty corpus (OPTIONAL, aggregation, property paths, multi-hop, negatives) and captures a **genuine live-model baseline** (OpenAI provider) so that a future few-shot lift (Phase 7) is *measurable* against something with headroom. "Good" = a corpus that exercises the ways a bare generator actually fails, a defensible canonical-algebra judge, and a reproducible, credentials-gated live baseline that CI never needs secrets to reproduce (scripted stays the no-network default).

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this evaluation system -->
1. **Judge false-positives/negatives** — the canonical-algebra comparator must not mark a semantically-wrong query as correct (or vice-versa); string-match judging is forbidden.
2. **A corpus with no headroom** — if gold cases are near-ceiling on the baseline, few-shot cannot show a measurable delta and the phase's purpose is void.
3. **Secret leakage** — the live-model baseline run must never commit provider keys or raw request/response bodies; scripted CI must stay key-free.
4. **Baseline non-reproducibility** — a checked-in live baseline that cannot be regenerated from documented steps (model, temperature, corpus revision) is not a baseline.
5. **Transpiler regression masked as eval work** — touching the deterministic SPARQL→AQL transpiler (W3C ≥96.4%) while editing the eval harness.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Enterprise semantic data integration / knowledge-graph engineering — the AI discipline is **KGQA (knowledge-graph question answering) / semantic parsing**, deployed as the query front-end of an OBDA / Virtual Knowledge Graph (the Contextual Data Fabric, `P = (O, M, S)`). The fabric itself federates over cross-domain enterprise sources (finance, operations), but the artifact under evaluation is domain-agnostic: an English question turned into a **conceptual SPARQL IR** over an aligned OWL/Turtle ontology.

**User Population:** Two tiers, plus the eval authors. (1) *Machine consumer (primary):* the CDF live-path pipeline itself — the M5 partition planner splits the SPARQL IR by source, routes a relational leg through Ontop (SPARQL→SQL / R2RML) and an Arango leg through this repo (SPARQL→AQL), M6 joins partial results on canonical entity keys, and M7 wraps a grounded, cited envelope. The SPARQL IR is a *machine contract*, not a human-read query. (2) *End user (ultimate):* enterprise analysts / business users who ask English questions on the `/federate` endpoint and act on the cited answer — they never see the SPARQL. (3) *Eval domain experts:* the semantic-web engineers who author gold SPARQL and calibrate the canonical-algebra judge.

**Stakes Level:** **High.** Not safety-critical, but the SPARQL IR is the **front door of the live federated path** — there is no human in the loop to eyeball the query before it executes. A query that is *parseable and even transpilable but semantically wrong* propagates silently: every downstream stage faithfully returns a confidently-wrong, **cited** answer that a business user will act on. The danger is not crashes (those are caught) but plausible-looking wrong queries.

**Output Consequence:** The generated SPARQL is decomposed → routed to SQL (Ontop) and AQL (this repo) legs → joined on entity keys (M6) → returned inside a citation envelope (M7, "cite the exact query, or refuse"). Because the answer is *cited to the query*, **query correctness is citation integrity**: a wrong IR manufactures a false citation. No stage re-validates intent against the original English, so an incorrect IR is never self-corrected downstream.

### What Domain Experts Evaluate Against

<!-- Practitioner-language rubric ingredients grounded in KGQA/SPARQL eval literature and SPARQL 1.1 semantics. Feed these to the eval-planner (Sections 5-7). -->

**Dimension: IRI / prefix grounding (no hallucinated URIs)**
- *Good (expert accepts):* every class and property IRI, and every declared prefix, resolves to a term that actually exists in the supplied OWL/Turtle ontology; the query uses the ontology's real names.
- *Bad (expert flags):* invents a plausible-looking IRI or prefix from the question's wording (e.g. emits `:emailAddress` or `foaf:mbox` when the ontology defines `:email`), or leans on a lexicalized name that happens to read well.
- *Stakes:* **Critical.**
- *Source:* PGMR — direct LLM generation hallucinates a URI in **75.4%** of queries on average (up to 96% on QALD-10); T2S-Metrics defines *URI Hallucination* and *URI Exact Match* as first-class structural metrics; FAULT shows systems hallucinate predicates/entity IRIs from their names (hence its opaque-IRI test sets).

**Dimension: Triple-pattern structural fidelity (BGP shape)**
- *Good:* the basic graph pattern contains exactly the triples the question entails — every required hop present, no redundant or over-broad triple, join variables shared correctly.
- *Bad:* missing a required triple, adding a redundant/over-broad triple that widens the answer set, or dropping a join variable so two patterns no longer connect.
- *Stakes:* **Critical.**
- *Source:* FIRESPARQL identifies "structural inconsistencies — missing or redundant triples" as one of its two dominant error categories; our SOTA survey flags over-broad BGPs.

**Dimension: Aggregation & grouping correctness (GROUP BY)**
- *Good:* when the question asks to count/sum/average per something, every non-aggregated projected variable appears in `GROUP BY`, and the aggregate is applied to the group the question implies (SPARQL 1.1 §11.4).
- *Bad:* an aggregate in `SELECT` alongside a non-aggregated projected variable that is *not* in `GROUP BY` (invalid SPARQL 1.1), or aggregating over the wrong grouping key so the counts answer a different question.
- *Stakes:* **High.**
- *Source:* SPARQL 1.1 §11.4 / §18.2.4.1; FIRESPARQL reports unaggregated-projection ("Variable ?x is selected but not aggregated") as a top error class; long-standing practitioner reports on Jena/Sesame ("variable not present in GROUP BY").

**Dimension: OPTIONAL vs. required semantics (answer cardinality)**
- *Good:* attributes the question marks as conditional ("…and their email *if they have one*") are wrapped in `OPTIONAL`; genuinely required constraints stay in the mandatory BGP, preserving the intended answer cardinality.
- *Bad:* wrapping a required pattern in `OPTIONAL` (silently over-returns rows that fail the constraint), or making a conditional attribute mandatory (silently *drops* valid answers, or empties the result set entirely).
- *Stakes:* **High.**
- *Source:* practitioner reports on OPTIONAL misuse producing empty/incorrect result sets; our SOTA survey lists "wrong cardinality via missing OPTIONAL."

**Dimension: Property-path & multi-hop correctness (with type compatibility)**
- *Good:* multi-hop relations use the correct property-path operator and direction (`/`, `^`, `+`, `*`) or an explicit join chain, applied only to subjects whose declared `rdfs:domain`/`rdfs:range` in the ontology are compatible.
- *Bad:* wrong path direction, a missing transitive `+`/`*`, or "type blindness" — applying a property whose declared domain is incompatible with the subject's class.
- *Stakes:* **High.**
- *Source:* SAGA — "type blindness" (property applied to a domain-incompatible entity) accounts for **64.3%** of SPINACH's failures on QALD-7; our SOTA survey lists property-path correctness and multi-hop as core difficulty axes.

**Dimension: Honest refusal / answerability**
- *Good:* when the question references a class or property absent from the ontology, or is otherwise unanswerable against the schema, the system surfaces an explicit unsupported/refusal signal rather than fabricating a query over invented terms.
- *Bad:* emits a confident, well-formed SPARQL over hallucinated terms for a question the ontology cannot answer (the negative-case trap).
- *Stakes:* **High.**
- *Source:* this repo's hard rule — raise `UnsupportedSparqlError`, never emit silently-wrong output; FAULT's opaque-IRI controlled tests (a system must not depend on lexicalized names); this phase's explicit "negatives" corpus requirement.

### Known Failure Modes in This Domain

- **URI / prefix hallucination** — inventing IRIs and prefixes from the question's surface wording rather than the ontology. The single dominant NL→SPARQL failure (≈75% of bare-generation queries; the exact mode PGMR/FAULT target). Manifests here as terms like `:emailAddress` that read plausibly but aren't in the OWL/Turtle schema.
- **Silently-wrong-but-parseable queries** — the most dangerous mode for *this* deployment: the query passes rdflib parse and even transpiles to non-empty AQL, but encodes *different semantics* than the question. String-match and easy-data execution judging both miss it; only the **canonical-algebra judge** (this repo's judge of record) catches it. This is why string-match judging is forbidden.
- **Aggregation-without-grouping** — aggregate functions with unaggregated projected variables and no `GROUP BY` (invalid SPARQL 1.1), or aggregation over the wrong key.
- **Wrong cardinality via OPTIONAL misuse** — required-vs-optional confusion that over-returns or silently empties results.
- **Over-broad BGP / type blindness** — redundant triples or domain-incompatible property application that widen or corrupt the answer set.
- **OOD / unseen-template collapse** — near-ceiling on i.i.d. splits, then sharp drops on re-split / compositional / unseen-template questions (KGQA generalizability studies; the reason the harder corpus must include compositional and negative cases, not just single-BGP toys).

### Regulatory / Compliance Context

**No external statutory regime (HIPAA / GDPR / FCA) applies to this evaluation phase** — the corpus ontology is a synthetic conceptual schema (`http://ex.org/`, Person/Order-style toy terms) with no real PII, and the eval runs offline. The directly-relevant constraints are internal governance / data-handling rather than regulatory:

- **Secret & payload hygiene (in-scope, Critical):** the live-model baseline must never commit provider API keys or raw request/response bodies; the `scripted` CI path must stay credentials-free (Critical Failure Mode 3). Corpus/baseline are trusted checked-in repo data — no secrets, no PII.
- **Grounding-and-citation obligation (deployment context):** because the downstream M7 envelope cites the exact query, the fabric's "cite or refuse" posture makes *query correctness the integrity of the citation* — a governance obligation this eval indirectly protects, not a law.
- **Deferred to production, out of scope here:** if the fabric federates over regulated tenant data in production, tenant-scoping and write-op guardrails (adapter seam 5, currently unimplemented) become the compliance surface. Phase 06.2 evaluates a zero-shot, guardrail-free generator over a synthetic ontology, so those controls are explicitly not exercised.

## 2. Framework Decision

> **Pre-filled by the orchestrator, not the interactive framework-selector.** The stack is architecturally fixed by this repo's non-negotiable hard rules (`rdflib` for SPARQL parsing, the shared `arango-query-core` engine, no custom parser/judge), so there is no open framework choice to make — only pinning and rationale.

**Selected Framework:** Existing in-repo eval stack — `tests/nl2sparql/eval/` harness (`runner.py`) + `rdflib` **canonical-algebra** judge + `arango_query_core.nl.NLQueryEngine` (via this repo's `SparqlAdapter`) + OpenAI provider for the live baseline. No new framework is introduced.

**Version:** `rdflib` and `arango-query-core` are pinned by `pyproject.toml` (`arango-query-core` at the git ref in the `nl` extra; `hatchling` `allow-direct-references` enabled). Live provider: OpenAI `gpt-4o-mini` per the existing `configs.yml` `openai` config. Pin the exact model + corpus revision in the checked-in baseline artifact.

**Rationale:**
The repo's hard rules mandate `rdflib` parsing and the shared engine; a custom parser or a bespoke judge is explicitly forbidden. Canonical-algebra equivalence (already implemented in `runner.py::_canonical`) is the settled judge of record. Phase 06.2 is an *evaluation-hardening* phase, so the "framework" is the harness that already exists — the work is corpus authorship and a live-provider baseline capture, not new infrastructure.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Custom SPARQL parser / bespoke judge | Forbidden by repo hard rules (rule-000); `rdflib` + canonical algebra is mandated |
| String / exact-match judging | Rejected in Phase 6 — brittle to variable naming, prefix, and triple ordering; canonical algebra is the invariant |
| LLM-as-judge | Deferred — adds cost, non-determinism, and a second model dependency; the deterministic transpiler + rdflib uniquely lets us avoid it. Revisit only if canonical algebra proves insufficient |
| External KGQA corpora as drop-in (QALD/LC-QuAD 2.0/Spider4SPARQL) | Wikidata/DBpedia schemas, not our OWL/Turtle conceptual ontology — use only to *seed difficulty patterns*, never as the corpus |
| Anthropic / other live provider | OpenAI `gpt-4o-mini` is already wired in `configs.yml`; keep the baseline provider consistent with existing config |

**Vendor Lock-In Accepted:** Partial — the live baseline pins OpenAI `gpt-4o-mini`, but the harness is provider-agnostic (scripted + pluggable configs), so re-baselining on another provider is a config change, not a rewrite.

The judge — the single most important line of the harness — is canonical **algebra**
equality, never string match (rule 200):

```python
# tests/nl2sparql/eval/runner.py
def _judge_canonical(expected: str, outcome) -> bool:
    if not outcome.aql:                      # transpiler REJECTED the SPARQL -> fail (Pitfall 4)
        return False
    ce = _canonical(expected)                # _stable_repr(parse_sparql(expected).algebra)
    ca = _canonical(outcome.sparql)          # PYTHONHASHSEED-stable: sets/PV sorted before repr
    return ce is not None and ce == ca
```

### The Two YAML Shapes You Author

Corpus case (`corpus.yml`, under `cases:`) — the unit of work for 06.2:

```yaml
- name: optional-email            # unique id; becomes the baseline.json per-case key
  nl: "List people and their email address if they have one."
  expected: |                     # GOLD SPARQL — the canonical-algebra judge target
    PREFIX : <http://ex.org/>
    SELECT ?s ?e WHERE { ?s a :Person . OPTIONAL { ?s :email ?e } }
  # --- optional fields the runner honours ---
  scripted: |                     # what the no-network `scripted` client replays (defaults to `expected`)
    PREFIX : <http://ex.org/>
    SELECT ?s ?e WHERE { ?s a :Person . OPTIONAL { ?s :email ?e } }
  ontology: |                     # per-case Turtle override (defaults to the top-level `ontology:` block)
    @prefix : <http://ex.org/> . ...
  params: {min_age: 30}           # bind-var params applied only at the FINAL re-translate
  data: |                         # optional Turtle fixture; presence enables the `execution` judge tier
    :p1 a :Person ; :email "a@x.org" .
```

Provider/judge config (`configs.yml`, under `configs:`):


### Common Pitfalls
1. **The runner's live path reads `NL2SPARQL_API_KEY`, not `OPENAI_API_KEY`.** `runner._client_for` builds `OpenAICompatibleClient(provider="openai", model=...)` with no key arg, so it falls to `os.getenv("NL2SPARQL_API_KEY", "")`. The `OPENAI_API_KEY` fallback only exists in `get_default_client()`, which the runner does **not** use. Export `NL2SPARQL_API_KEY` (+ optional `NL2SPARQL_MODEL`/`NL2SPARQL_BASE_URL`) or the sweep posts an empty bearer and 401s.
2. **`write_report()` output ≠ `baseline.json` schema.** `write_report` writes `{config, pass_rate, cases:[{name,passed,elapsed_ms}]}` into gitignored `reports/`; `baseline.json` is the nested `{configs:{…}}` gate. Promoting a live run into `baseline.json` is a **manual, human-reviewed** step (same discipline as goldens — never auto-regenerate in CI).
3. **`ScriptedLLMClient` replays its LAST response forever once drained.** The runner builds a fresh client per case for exactly this reason; if you script cases yourself, one client per case, or case N-1's SPARQL leaks into case N.
4. **The judge requires BOTH a non-empty `outcome.aql` AND algebra equality.** A gold `expected` that is valid SPARQL 1.1 but that *this repo's deterministic transpiler cannot emit AQL for* is permanently un-passable (`aql == ""` → fail). Every gold must be transpilable, not merely parseable — verify each new gold round-trips through `api.translate` before committing.
5. **A `scripted` case tests the judge, not the model.** The scripted client replays `case["scripted"]` (or `expected`), so it passes trivially unless you author a deliberate `scripted:` near-miss (see `deliberate-near-miss`, which keeps the gate < 1.0). **Headroom is only measurable on the live config** — do not read the scripted pass-rate as model accuracy.
6. **Pin temperature + model + corpus SHA, or the baseline is not reproducible.** `OpenAICompatibleClient` hardcodes `temperature=0.1` and sends **no `max_tokens`**; `configs.yml` can override neither today. gpt-4o-mini is not bit-deterministic even at low temperature, so the baseline artifact must record model, temperature, and the corpus git SHA to be interpretable on re-run (Critical Failure Mode 4).

## 4. Implementation Guidance

**Model Configuration:**
- **Live baseline model:** OpenAI `gpt-4o-mini` (pinned in `configs.yml` under the `openai-gpt4o-mini` config; matches `cost.py`'s priced entry: `$0.00015`/1k input, `$0.0006`/1k output).
- **Temperature:** `0.1` — hardcoded in `OpenAICompatibleClient.__init__` (`_BaseHttpClient` default). `configs.yml` cannot override it today; keep it at `0.1` for the baseline and **record it in the artifact** rather than assuming reproducibility.
- **`max_tokens`:** unset on the OpenAI-compat path (only `AnthropicClient` pins `max_tokens=4096`). Acceptable for a SPARQL baseline (completions are short), but note it as a known unbounded surface (see §4b.3).
- **`max_repairs`:** `2` (config-level) → the engine runs up to `max_retries + 1 = 3` provider calls per case (generate + 2 repairs). This is the retry budget the SOTA survey flags as *unmeasured* (Q4) — the live baseline is the first datapoint.
- **Corpus revision:** pin the `corpus.yml` git SHA in the baseline artifact — a pass-rate without a corpus revision is meaningless (Critical Failure Mode 4).
- **Judge:** `canonical` (rdflib algebra); switch a case to the `execution` tier only when it carries a `data:` Turtle fixture (cross-validated via `tests.helpers.oxi` / pyoxigraph).

**Core Pattern:**
Two distinct workflows land in 06.2 — neither changes the generator or the transpiler.

1. *Author a harder gold case* (the bulk of the work). Seed difficulty from the SOTA survey's patterns (OPTIONAL, aggregation, property paths, multi-hop, negatives), but author gold against **this repo's OWL/Turtle conceptual ontology**, never Wikidata/DBpedia. Every gold must (a) parse via rdflib and (b) transpile to non-empty AQL, or the judge can never pass it:

```python
from arango_sparql.translate.resolver import SchemaResolver
from arango_sparql.api import translate as api_translate
```

**Tool Use:**
No LLM tool/function-calling — the model's only job is to emit a fenced ```` ```sparql ```` block (rule 300: never ask the LLM for AQL). The "tools" are internal seams: `EngineProviderBridge` runs each completion through `extract_sparql_from_response` before the engine sees it; `SparqlAdapter.validate` calls the deterministic transpiler (`api.translate`) as the parse-or-fail gate; `SparqlAdapter.repair_hint` reproduces `format_repair_context` (`[CODE] msg` + SPARQL-1.1 hint) on the retry turn. The judge's optional `execution` tier is the only place pyoxigraph is touched, lazily imported so its absence never breaks canonical judging.

**State Management:**
The eval harness is **stateless and idempotent by design** — every case rebuilds its own `SchemaResolver`, `LLMClient`, and `NlPipeline`, so cases can't leak state into one another (the fresh-client-per-case rule exists precisely because `ScriptedLLMClient` replays its last response). The only *persistent* state is the checked-in `baseline.json` (the regression gate) and the gitignored `reports/`. There is no conversation memory, no SQLite corrections cache in this path, and no cross-run mutable global — that is a feature for a deterministic eval, not a gap.

**Context Window Strategy:**
The system prompt = SPARQL-1.1 grammar + house rules + the **full ontology Turtle** (`PromptBuilder.render_system`). For 06.2's small conceptual ontology this is far under gpt-4o-mini's 128k window, so truncation is a non-issue; the real lever is **prompt-prefix caching**. The system turn is byte-stable per ontology and the repair hint is appended to the *user* turn only, so the static prefix stays cacheable — OpenAI's automatic caching surfaces hits as `usage.prompt_tokens_details.cached_tokens` (captured into `LLMResponse.cached_tokens`). Keep the ontology minimal per case (rule 300: pre-trim to reachable classes/properties) so that as the corpus grows the prompt does not; if a future large-ontology case ever approaches the window, slice the Turtle to the case's classes rather than truncating mid-graph.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

The LLM's structured output here is deliberately **not** JSON — it is a fenced SPARQL block, and the "schema" it must satisfy is the SPARQL-1.1 grammar enforced by **rdflib parse + deterministic transpile** (rule 300 forbids asking the model for JSON/AQL). So the framework-appropriate Pydantic use is not `response_format` on the completion; it is **validating the two artifacts you author** — the corpus case and the baseline — so a malformed corpus can never silently skew a baseline. The runner currently loads both with bare `yaml.safe_load`; add a load-time Pydantic gate:

```python
from pydantic import BaseModel, Field, field_validator
from arango_sparql.translate.parser import parse_sparql  # rdflib parseQuery+translateQuery

class CorpusCase(BaseModel):
    name: str = Field(min_length=1)
    nl: str = Field(min_length=1)
    expected: str = Field(min_length=1)          # gold SPARQL — the judge target
    scripted: str | None = None                  # what the no-network client replays
    ontology: str | None = None                  # per-case Turtle override
    params: dict[str, object] | None = None
    data: str | None = None                      # presence enables the `execution` judge tier

    @field_validator("expected")
    @classmethod
    def _gold_must_parse(cls, v: str) -> str:
        parse_sparql(v)                          # raises SparqlParseError if the gold is unparseable
        return v

class BaselineConfig(BaseModel):
    pass_rate: float = Field(ge=0.0, le=1.0)
    passed: int = Field(ge=0)
    total: int = Field(ge=1)
    cases: dict[str, bool]
    model: str | None = None                     # ADD for the live config (reproducibility)
    temperature: float | None = None             # pin: 0.1
    corpus_sha: str | None = None                # pin: corpus.yml git SHA
```

**Two-layer validation, no silent acceptance:** (1) `CorpusCase` rejects a malformed/unparseable gold at *load* time; (2) the transpilability + canonical-algebra check (`api.translate` non-empty `aql` + `_canonical is not None`) is the deeper gate before a gold is committed. **Retry logic:** the *model's* retries are the engine's repair loop (`max_repairs=2` → up to 3 calls, error-fed via `repair_hint`); the *authoring* pipeline gets zero retries — a Pydantic/parse failure is surfaced immediately (fail the corpus load, don't skip the case), because a skipped case is a hidden hole in coverage (Critical Failure Mode 2).

### Async-First Design

The harness and every client are **synchronous and sequential on purpose** (`requests.post`, blocking; `runner.run` iterates cases in file order). This is the correct choice for a deterministic eval — report ordering, `elapsed_ms`, and provider rate-limit behavior all stay stable. **The one mistake to avoid:** parallelizing corpus cases (`asyncio.gather` / thread pool) to speed up a live sweep — it makes latency non-reproducible, risks interleaved rate-limit 429s that flip pass/fail nondeterministically, and buys nothing for the scripted CI gate (which does no I/O). If a very large live corpus ever needs speedup, bound concurrency explicitly and preserve deterministic case ordering in the emitted report. **Stream vs. await:** always await the full completion — never stream. Fence extraction (`extract_sparql_from_response`) and canonical validation both need the *entire* query text; a streamed partial can't be parsed or judged.

### Prompt Engineering Discipline

- **System vs. user separation is load-bearing here.** `PromptBuilder.render_system` (grammar + house rules + ontology) is byte-stable per ontology; the repair hint is appended to the **user** turn only (`_REPAIR_USER_SUFFIX`). This is not stylistic — it keeps the cacheable prefix identical across retries and across cases so OpenAI's automatic prompt cache (and the Anthropic `## Examples` split point) actually hit.
- **Few-shot: keep it zero-shot for 06.2.** The pipeline pins `few_shot_k=0` and `SparqlAdapter.few_shot_index()` returns `None`. That is intentional — the whole point of the live baseline is to measure the **bare** generator so Phase 7's dense/BM25 few-shot lift (SOTA survey #1) has *measurable headroom*. Do not add exemplars in this phase; if you did, you would be measuring the wrong baseline.
- **Token budget:** `temperature=0.1` pinned; set an explicit `max_tokens` before any *production* rollout (the OpenAI-compat client leaves it unbounded — fine for short SPARQL in a controlled sweep, a footgun anywhere user input drives length). SPARQL completions are tiny (tens–low hundreds of tokens), so the budget lever is the prompt (ontology) size, not the completion.

### Context Window Management

Not a RAG/conversation system — there is no chunking or summarization. The context is one static system prompt (grammar + ontology) plus one short user turn per attempt. Management strategy: **minimize and stabilize the ontology block.** Pre-trim per-case Turtle to the classes/properties the question can reach (rule 300) so the prompt stays small and byte-stable → prefix-cacheable and cheap. gpt-4o-mini's 128k window means the tiny 06.2 ontology is nowhere near the limit; the only compaction that matters is *not re-sending a bloated ontology every case*. If a future case needs a genuinely large schema, slice the Turtle to the reachable subgraph rather than truncating arbitrarily (a truncated ontology would drop exactly the class the model needs and induce IRI hallucination — the failure PGMR targets in the SOTA survey).

### Cost and Latency Budget

- **Per-call estimate (gpt-4o-mini, from `cost.py`):** input `$0.00015`/1k, output `$0.0006`/1k. A case ≈ 500–1500 prompt tokens (grammar + small ontology) + ~100 completion tokens ≈ **$0.0002–$0.0004 per call**. With `max_repairs=2` (up to 3 calls) and a ~30-case hardened corpus, a **full live sweep ≈ 1–3 US cents** — cost is a non-issue; the value is the reproducible number, not the spend.
- **Caching:** two tiers. (1) The `scripted` config is the ultimate cache — $0, no network — and stays the CI default. (2) On live sweeps, the byte-stable system prefix earns OpenAI automatic prompt-cache discounts, surfaced as `usage.prompt_tokens_details.cached_tokens` → `LLMResponse.cached_tokens` → the `LLMCallRecord` audit trail; optionally set a `prompt_cache_key` per ontology to steer routing. No exact-match/semantic response cache is needed at this volume.
- **Model routing:** gpt-4o-mini is already the cheap tier — no sub-task routing (classification/summarization models) applies to a single-shot SPARQL generation. The "routing" decision that matters is operational: **scripted for CI, live only for a deliberate baseline refresh** — never let the live provider onto the default `pytest` path (rule 200: eval is gated behind `RUN_EVAL=1`).

## 5. Evaluation Strategy

> **Self-referential note.** Phase 06.2's deliverable *is* this evaluation upgrade — a harder corpus + a genuine live-model baseline — so the strategy below is concrete about *this* repo's harness, not a generic plan. Every dimension is measured **CODE-first** by the settled judge of record: rdflib **canonical-algebra equivalence** (`runner._canonical` → `_stable_repr` → equality, plus the `outcome.aql != ""` transpilability gate in `_judge_canonical`). String-match judging is forbidden (Critical Failure Mode 1; rule 200). LLM-as-judge is deliberately *not* used — the deterministic transpiler + rdflib uniquely let us avoid its cost/non-determinism (see §2 Alternatives). Human review is reserved for one meta-dimension only: calibrating the judge itself.

### Dimensions

Each row below is one Section-1b practitioner rubric ingredient, turned into a corpus difficulty class and wired to the canonical-algebra judge. The judge does not score dimensions in isolation — it is whole-query algebra equivalence — so "Measurement" states which structural feature of the canonical algebra a case in that class *exercises*, and each such case is authored to isolate that feature (the deliberate near-miss discipline generalized per dimension).

| Dimension (Section-1b ingredient) | Rubric — PASS / FAIL (domain language) | Measurement Approach | Priority |
|-----------|----------------------------|---------------------|----------|
| **IRI / prefix grounding** (no hallucinated URIs) | **PASS:** every class/property IRI and declared prefix in the emitted SPARQL resolves to a term in the supplied OWL/Turtle ontology; canonical algebra matches gold. **FAIL:** invents a plausible IRI/prefix from question wording (e.g. `:emailAddress` when the ontology defines `:email`) → algebra diverges from gold, or the transpiler rejects the unknown term (`outcome.aql == ""`). | **Code** — canonical-algebra equality (`_judge_canonical`); hallucinated IRIs surface as either an algebra mismatch or a transpile rejection. No LLM judge. | **Critical** |
| **Triple-pattern structural fidelity** (BGP shape) | **PASS:** the BGP contains exactly the triples the question entails — every required hop, no redundant/over-broad triple, join variables shared correctly; algebra == gold. **FAIL:** a missing triple, a redundant/over-broad triple, or a dropped join variable → `_stable_repr` of the BGP diverges from gold. | **Code** — canonical algebra (the `BGP.triples` + join-variable structure is exactly what `_stable_repr` canonicalizes). No LLM judge. | **Critical** |
| **Aggregation & grouping** (GROUP BY) | **PASS:** every non-aggregated projected variable appears in `GROUP BY` and the aggregate keys on the group the question implies (SPARQL 1.1 §11.4); algebra == gold. **FAIL:** an unaggregated projected variable absent from `GROUP BY` (invalid SPARQL 1.1 → parse/transpile fail) or grouping on the wrong key → algebra mismatch. | **Code** — canonical algebra over the `AggregateJoin`/`Group`/`Extend` nodes; invalid-grouping cases fail via the transpile gate. No LLM judge. | **High** |
| **OPTIONAL vs. required** (answer cardinality) | **PASS:** conditional attributes ("…email *if they have one*") are wrapped in `OPTIONAL`, required constraints stay in the mandatory BGP; algebra == gold. **FAIL:** a required pattern wrapped in `OPTIONAL` (over-returns) or a conditional attribute made mandatory (silently drops/empties results) → `LeftJoin` vs `BGP` structure diverges from gold. | **Code** — canonical algebra distinguishes `LeftJoin` (OPTIONAL) from mandatory `BGP`/`Join`. No LLM judge. | **High** |
| **Property-path & multi-hop** (with type compatibility) | **PASS:** multi-hop relations use the correct path operator/direction (`/`, `^`, `+`, `*`) or explicit join chain, applied only to `rdfs:domain`/`rdfs:range`-compatible subjects; algebra == gold. **FAIL:** wrong direction, missing transitive `+`/`*`, or "type blindness" (domain-incompatible property) → path algebra diverges, or the transpiler rejects a domain-incompatible term. | **Code** — canonical algebra over path nodes; type-blindness cases surface via algebra mismatch or the transpile gate. No LLM judge. | **High** |
| **Honest refusal / answerability** (the negatives trap) | **PASS:** for a question referencing a class/property absent from the ontology (or otherwise unanswerable), the generator surfaces an explicit unsupported signal and emits **no** transpilable query (`UnsupportedSparqlError` / `outcome.aql == ""`). **FAIL:** emits a confident, well-formed, transpilable SPARQL over hallucinated terms. | **Code** — *inverted* accept signal (see "Scoring negatives" below): PASS iff `outcome.aql == ""`; FAIL iff a non-empty AQL is produced. No gold algebra to match. No LLM judge. | **High** |
| **Judge fidelity / calibration** (meta) | **PASS:** the canonical-algebra comparator marks a semantically-correct query correct and a semantically-wrong one wrong, on audited samples. **FAIL:** a false-pass (wrong query judged correct) or false-fail (correct query judged wrong) — Critical Failure Mode 1. | **Human** — the judge calibrator audits false-pass/false-fail on live-baseline samples and maintains the deliberate near-miss that keeps the scripted gate < 1.0. This is the only non-code dimension. | **Critical** |

**Scoring negatives (abstention/refusal — external precedent is weak, so we define it).** A negative case cannot be scored by algebra equality because there is no valid gold query. We define a concrete, still-code-based convention: a negative case carries an explicit marker (e.g. `expect_refusal: true`); its PASS condition is the **inverse** of the positive judge — PASS iff the pipeline raises `UnsupportedSparqlError` *or* returns `outcome.aql == ""` (no transpilable query), FAIL iff it emits a non-empty transpilable AQL over invented terms (the silently-wrong-but-parseable trap). This is a **minimal, reviewed extension to `runner._judge`** (a marker branch), not a new judge type and not an LLM judge; it keeps the accept signal deterministic. Because the corpus `CorpusCase` schema (§4b) requires a non-empty `expected`, a negative case's `expected` field holds a short human-readable refusal rationale (documentation only, never parsed as gold) — the executor pins the exact field convention when implementing the marker branch. This negative-scoring convention is itself a **measurement contribution** (see "SOTA gaps this corpus measures" below): honest-refusal scoring for NL→SPARQL has no settled external benchmark.

## 7. Production Monitoring

> **Framing.** There is no "production" inference service in Phase 06.2 — the artifact is an **offline eval harness**. "Monitoring" is therefore reframed as **baseline-regression tracking over time**: does the harness still hold the line as the corpus, the generator, and (later) the few-shot layer evolve? The monitored surface is `baseline.json` + the `test_eval.py` gate + gitignored `write_report()` artifacts, not a request stream.

**Tracing Tool:** **In-repo — no external tracer** (Arize Phoenix default explicitly overridden, see §5 "Tracing-default override"). The three in-repo mechanisms are the trace/monitor stack: (1) **`baseline.json`** — the checked-in per-config, per-case regression gate; (2) **`write_report()`** JSON+Markdown under gitignored `reports/` — the per-sweep record; (3) the per-call **`LLMCallRecord`** audit trail (`EngineProviderBridge`) — tokens, `cached_tokens`, latency, and repair count on live sweeps. Adopting Phoenix/Langfuse here would add a dependency and a network surface for an offline harness that already emits everything it needs — revisit only if/when the generator is exposed as a live `/federate` service (out of scope, §1b).

**Key Metrics to Track:**
1. **Scripted pass-rate** (the CI gate) — must stay ≥ `baseline.json` scripted `pass_rate`, with no baseline-passing case regressing and every new case green before entry.
2. **Live per-dimension pass-rate breakdown** — `openai-gpt4o-mini` pass-rate overall and per difficulty class (IRI/BGP/agg/OPTIONAL/path/negative); the headroom signal for Phase 7.
3. **W3C DAWG no-regression guard** — the deterministic SPARQL→AQL transpiler must stay **≥ 96.4%** query-eval (Critical Failure Mode 5); eval-harness work must never touch or regress it.
4. **Live-sweep cost & latency** — total sweep cost (target ≈ 1–3¢ / ~30 cases) and per-case `elapsed_ms`, plus prompt-cache hit rate (`cached_tokens`).
5. **Repair-loop retry distribution (Q4)** — per-case call count under `max_repairs=2`; the survey's unmeasured retry-budget gap.

**Alert Thresholds (what fails the build / what a human reviews):**
- **Fail CI:** scripted `pass_rate` < baseline, OR any baseline-passing case now failing, OR a new corpus case not passing before it enters `baseline.json` (all enforced today by `test_eval.py`).
- **Fail CI (invariant):** W3C DAWG query-eval < **96.4%**.
- **Human review before re-promoting `baseline.json`:** a live per-dimension class dropping to ~0, a confirmed judge false-pass/false-fail, or the corpus losing headroom (live pass-rate approaching 1.0 → Critical Failure Mode 2).
- **Investigate (not paging):** live-sweep cost or latency spiking well above the cent/seconds scale (usually a bloated-ontology prompt-cache miss).

**Smart Sampling Strategy (which live outputs a human reviews):** weight review toward the interactions most likely to carry signal — (a) cases that consumed **repairs** (≥ 1 retry via the `LLMCallRecord` trail) — the model struggled; (b) cases whose emitted algebra **diverged from gold** (FAIL) — candidate false-fails or genuine misses; (c) **negative cases that emitted a query** — the silently-wrong-but-parseable trap, the single most dangerous mode for this deployment (§1b); (d) canonical-vs-execution **judge disagreements** on `data:`-bearing cases. Route (a)/(b)/(d) to the judge calibrator, (c) to the ontology owner. This mirrors `ai-evals.md`'s signal-based sampling (retries, divergence, escalation-analogs) rather than uniform sampling.
