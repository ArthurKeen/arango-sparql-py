<objective>
Grow `corpus.yml` from single-BGP toys to real-difficulty **positive** cases across the
Section-1b difficulty classes: **OPTIONAL** cardinality (`LeftJoin`), **aggregation /
GROUP BY** (`AggregateJoin`/`Group`), **property paths** across the operators this repo's
deterministic transpiler actually SUPPORTS — SequencePath `:p/:q`, InvPath `^:p`, MulPath
`:p+`/`:p*`/`:p?` (lowered to a bounded UNION of fixed-length arms via
`arango_sparql.translate.paths._emit_mul_path`), AlternativePath `:p|:q` (via
`arango_sparql.translate.union_paths.emit_alternative_path`), and forward NegatedPath
`!:p` / `!(:p|:q)` (via `_emit_negated_path`) — and **multi-hop** via explicit join chains
(multi-triple BGP). Extend the shared `ontology:` block with the terms these classes need
(an object-property relationship for aggregation/multi-hop, an optional datatype property
for OPTIONAL), mirroring the phys idiom already used in
`tests/translate/{hybrid,edge_traversal}.yml`. Land a permanent **authoring guard**
(`test_gold_transpilable.py`) that asserts every non-refusal gold parses via rdflib AND
transpiles to non-empty AQL.

Purpose: These positive classes give the corpus its difficulty spine and are the cases
the canonical-algebra judge scores directly (NL-EVAL-03 SC1). Every gold is verified
transpilable at authoring time so it can never become un-judgeable (AI-SPEC Pitfall 4 /
Guardrail "Gold transpilability gate"). **Only the inverse-arm negated path `!(^:p)`
remains unsupported** (raises `UnsupportedSparqlError` "negated property paths with inverse
arms") — that single form is a Plan 03 negative; every other path operator above is a
POSITIVE case authored here. This plan touches ONLY corpus data + a guard test; the
generator and transpiler are untouched (W3C ≥ 96.4% preserved).
Output: an extended `corpus.yml` + a transpilability guard test.
</objective>
